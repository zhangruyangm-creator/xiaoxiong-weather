# 迷宫生成与可解性算法技术说明

> 对应模块：`:game:maze`（小熊迷宫，v1.13.0）
> 核心文件：`MazeGenerator.kt`、`MazeSolvability.kt`、`MazeGame.kt`、`MazeGameLogic.kt`、`MazeLevels.kt`、`MazeHintSession.kt`、`MazePlayField.kt`、`MazeRender.kt`、`MazeThemeArt.kt`、`MazeThemeDecor.kt`、`MazeOverlays.kt`、`MazeParticles.kt`、`MazeHud.kt`、`MazeLevelSelect.kt`、`BearMazeScreen.kt`
> 测试文件：`MazeGameLogicTest`、`MazeSolvabilityTest`、`MazeUndoHintTest`、`MazeHintSessionTest`、`MazeDailyTitleTest`、`MazeBoardLayoutTest`、`MazeParticlePoolTest`、`MazeDoorAnimationTest`、`MazeGameSessionTest`、`BearMazeEntryProviderTest`
> 摘要：本文说明小熊迷宫如何用「递归回溯雕刻」生成迷宫，如何在生成后叠加蜂蜜 / 冰面 / 钥匙锁 / 传送门四类玩法元素，如何用「带约束的状态空间 BFS」保证每一关都可解、无死锁；并补充提示系统（后台求解 + 代次校验）与渲染 / 性能架构（静态层烘焙、粒子环形池、reduceMotion）。

## 1. 背景与问题定义

小熊迷宫是一个以"小熊"为主角的推箱子式 2D 迷宫游戏。与常见走迷宫不同，它引入了四类**改变可达性语义**的格子：

| 格子 | 符号 | 语义 |
|------|------|------|
| 地板 | `.` | 可通行 |
| 墙 | `#` | 不可通行 |
| 起点 | `S` | 玩家初始位置 |
| 出口 | `E` | 通关目标；**需先收齐全部蜂蜜**才可离开 |
| 蜂蜜 | `H` | 收集物；未收集齐时出口关闭 |
| 冰面 | `I` | 进入后**沿当前方向持续滑行**，直到撞墙 / 撞不可通行格 |
| 钥匙 | `K` | 拾取后钥匙数 +1 |
| 锁门 | `L` | 需消耗 1 把钥匙才能通过（用后即开，不再消耗） |
| 传送门 | `1`–`9` | 同号成对，踩上即瞬移到另一端 |

**核心难点**：因为冰面的"滑行"会让玩家无法随意停在任一格、锁门会消耗钥匙、传送门会改变拓扑，所以**"这张迷宫图能不能通关"不再是一个普通 BFS 能直接回答的问题**。程序生成的关卡必须保证：

1. **可通关**（存在一条合法路径走到出口且收齐全部蜂蜜）；
2. **无死锁**（钥匙出现在锁门的"起点侧"，玩家不至于因拿不到钥匙而必然卡死）；
3. **有难度梯度**（越高难越复杂、元素越多，但始终可解）。

## 2. 迷宫图建模

关卡用字符网格表示，`MazeLevel.map: List<String>`，行 / 列数由内容决定（`MazeLevel.rows`、`MazeLevel.cols`）。`MazeLevel.parse()` 把字符图转为二维 `MazeCell` 数组；`MazeCell` 持有 `MazeTile` 与仅对传送门有意义的 `portalId`。这样的好处是：

- **人类可读、可手写**：前 12 关（`MAZE_HANDCRAFTED`）就是手工用字符画出来的教程关；
- **可序列化**：整局棋盘可编码成字符串，用于进程重建时恢复对局（`MazeSession`）；
- **纯数据、无 Android 依赖**：生成器与可解性判定都是纯 Kotlin 函数，便于单元测试。

```text
###########
#S....H...#
#.###.###.#
#...#...#.#
###.#.#.#.#
#...#.#...#
#.###.#####
#.....H..E#
###########
```

`MazeLevel.parse()` 与 `MazeGame` 中的 `tileToChar / charToCell` 使用同一套字符集，保证"生成 → 落盘 → 恢复"三处编码一致（`MazeTile.PORTAL` 用 `'1'..'9'` 表示，`portalId` 即字符本身）。

## 3. 迷宫生成算法

### 3.1 结构骨架：递归回溯（DFS 雕刻）

生成器采用经典的**递归回溯（Recursive Backtracking）**迷宫算法：

1. 棋盘初始全为墙 `#`，尺寸取**奇数**：列 `(11 + difficulty/5 × 2)` 截断在 `11–21`，行 `(9 + difficulty/6 × 2)` 截断在 `9–19`，随难度增长。
2. 从 `(1,1)` 起落脚，每次向四个方向**隔一格**（步长 2）探索，只要目标格是墙就打穿中间的格并递归。
3. 通过洗牌（`shuffle(rng)`）随机化探索顺序，产生不同迷宫形态。

```kotlin
val dr = intArrayOf(-2, 2, 0, 0)
val dc = intArrayOf(0, 0, -2, 2)

fun dfs(r: Int, c: Int) {
    carve(r, c)
    val order = intArrayOf(0, 1, 2, 3).also { it.shuffle(rng) }
    for (i in order) {
        val nr = r + dr[i]
        val nc = c + dc[i]
        if (nr in 1 until rows - 1 && nc in 1 until cols - 1 && g[nr][nc] == '#') {
            carve(r + dr[i] / 2, c + dc[i] / 2)   // 打通两格之间的墙
            dfs(nr, nc)
        }
    }
}
dfs(1, 1)
```

奇偶格策略保证所有通道宽度为 1，是"完美迷宫"（无环、任意两格间路径唯一）的典型构造。

### 3.2 出口选择：BFS 距离取最远格

为让关卡有"走到对面"的目标感，生成后跑一次 **BFS**（局部函数 `bfsDist`），把**距离起点最远的可达格**设为出口 `E`：

```kotlin
val start = 1 to 1
g[start.first][start.second] = 'S'
val distFromStart = bfsDist(start.first, start.second)
var exit = start
var best = -1
for (r in 1 until rows - 1) {
    for (c in 1 until cols - 1) {
        if (distFromStart[r][c] > best) {
            best = distFromStart[r][c]
            exit = r to c
        }
    }
}
g[exit.first][exit.second] = 'E'
```

这一步同时得到了 `distFromStart`——后续摆放元素时用它来施加空间约束，`best` 也是步数预算公式的输入（见 3.6 / 9）。

### 3.3 元素摆放与难度参数化

生成器按 `difficulty`（战役关≈关卡下标，无尽关≈波次换算）平滑解锁各元素。所有元素只落在"可达且非起点 / 出口"的地板池 `open`（`floors()` 过滤 `g[r][c] == '.' && distFromStart >= 0` 并 `shuffled(rng)`）：

| 元素 | 出现条件 | 数量 | 关键约束 |
|------|----------|------|----------|
| 蜂蜜 `H` | 始终 | `(2 + difficulty/4)` 截断 `2..10`，且 ≤ `MAX_SOLVE_HONEY - lockHoneyReserve` | 随机地板格；为锁旁附加蜂蜜预留预算 |
| 冰面 `I` | `allowIce && difficulty ≥ 2` | `(3 + difficulty/3)` 截断 `3..18` | 跳过起点紧邻（`distFromStart ≤ 2`） |
| 钥匙 `K` + 锁 `L` | `difficulty ≥ 4`（`open.size ≥ 3`） | 1 组；`difficulty ≥ 10` 时第 2 组（`open.size ≥ 4`） | 见 3.4 |
| 传送门 `1-9` | `difficulty ≥ 6` | `(1 + (difficulty-6)/8)` 截断 `1..3` 对 | 成对出现，两端从 `open` 头 / 尾取 |
| 捷径 | `difficulty ≥ 8` | `2 + difficulty/15` 次尝试 | 随机在两面以上邻接开放的墙上开洞 |

蜂蜜预算细节：`lockHoneyReserve = 2`（`difficulty ≥ 10`）/ `1`（`difficulty ≥ 4`）/ `0`，`honeyCount = budgetHoneyCount.coerceAtMost(MAX_SOLVE_HONEY - lockHoneyReserve)`，保证总蜂蜜数（含锁旁附加）不超过可解性判定上限 `MAX_SOLVE_HONEY`。

### 3.4 防死锁的"钥匙-锁"调度

这是生成器里最有设计含量的一部分。普通随机放钥匙 / 锁很容易产生**不可解关**（锁挡住了唯一通路，而钥匙在锁的"出口侧"永远够不到）。生成器用三条规则规避：

1. **锁放在唯一通路**：只选**真死胡同**（`openNeighborCount == 1`，只有唯一开放邻格）作为被锁住的蜂蜜位置，锁放在其**唯一通向处**，使"关蜂蜜的锁"无法被从旁绕开；
2. **钥匙必须落在锁的起点侧**：钥匙的 `distFromStart < 锁的 distFromStart`（`d in 2 until lockDist.coerceAtLeast(3)`，回退 `d in 1 until lockDist`），保证玩家**必须先经过钥匙、才能到达锁**；
3. **找不到安全钥匙位就整体撤回**——锁必须落在唯一通路上，钥匙必须落在起点侧。

```kotlin
val candidates = open.filter { (r, c) ->
    distFromStart[r][c] >= 4 && openNeighborCount(r, c) == 1   // 第 2 把锁要求 >= 5
}
...
val keySpot = open.firstOrNull { (r, c) ->
    val d = distFromStart[r][c]
    d in 2 until lockDist.coerceAtLeast(3)          // 钥匙须在锁的起点侧
} ?: open.firstOrNull { (r, c) ->
    distFromStart[r][c] in 1 until lockDist
}

if (keySpot != null) {
    open.remove(keySpot)
    g[keySpot.first][keySpot.second] = 'K'
} else {
    g[lr][lc] = '.'; open.add(lr to lc)             // 撤回锁位
    g[hr][hc] = '.'; open.add(hr to hc)             // 撤回蜂蜜位
}
```

"宁缺毋死锁"——如果当前随机布局配不出合法的钥匙位，就撤销这一组，而不是硬着头皮产出一个必然卡死的关。第 1 把锁要求死胡同 `distFromStart >= 4`，第 2 把（`difficulty >= 10`）要求 `>= 5`。

### 3.5 种子可复现

每个战役关由固定种子生成，**同一关永远同一张图**：

```kotlin
val seed = 0xBEEF0000L xor (i.toLong() * 0x9E3779B9L)
```

`0x9E3779B9`（黄金比例相关常数）用于把下标扩散成不相关的种子。无尽与每日模式沿用同一套派生规则：

- **无尽**：`cachedEndlessLevel(sessionSeed, wave, difficulty)`，`seed = sessionSeed xor (wave × 0x9E3779B9)`，键为 `(seed shl 8) or (wave and 0xFF)`；
- **每日**：`dailyMazeLevel(dateEpochDay)`，`seed = DAILY_SEED_SALT(0xDA11_0000L) xor (dateEpochDay × 0x9E3779B9)`，固定 `difficulty = 14`。

### 3.6 关卡缓存与轻量元数据

生成 1 关可能要跑多次可解性 BFS，因此模块内用**有界 LRU 缓存**（`MazeLevelCache`，基于 `LinkedHashMap` 的 `removeEldestEntry`）：

| 缓存 | 容量 | 键 |
|------|------|----|
| `campaignLevelCache` | `MAZE_CAMPAIGN_SIZE`（60） | 关卡下标 `i` |
| `endlessLevelCache` | `MAZE_LEVEL_CACHE_MAX`（128） | `(seed shl 8) or wave` |
| `dailyLevelCache` | 8 | `dateEpochDay` |

选关列表用轻量的 `MazeLevelMeta`（`mazeCampaignMeta` 直接读手写关常量 / 按 id 推主题与标题），**只有真正开始游玩某一关时才调用 `mazeCampaignLevel` 生成完整地图**，避免进入选关界面就批量生成全部 60 关。战役常量：手写关 `MAZE_HANDCRAFTED` 前 `MAZE_HANDCRAFTED_COUNT = 12` 关，战役总长 `MAZE_CAMPAIGN_SIZE = 60`。

## 4. 可解性判定：带约束的状态空间 BFS

### 4.1 为什么普通 BFS 不够

若迷宫只有墙和地板，用一次 BFS 即可判断可达性。但引入**蜂蜜需求、冰面滑行、钥匙消耗、传送门瞬移**后，"能不能通关"取决于**路径选择**，而不只是连通性：

- 明明物理可达，但**没收集齐蜂蜜** → 出口打不开；
- 冰面上**想停停不住** → 能到达的格子集合与"普通走法"不同；
- 钥匙 / 锁耦合 → 是否持钥、是否已开锁影响后续可达集合；
- 传送门 → 拓扑变化，且可形成捷径。

因此问题转化为：**在状态图 `(位置, 钥匙数, 蜂蜜掩码, 已拾取钥匙掩码, 已开锁掩码)` 上搜索是否存在一条能访问到"收齐蜂蜜后的出口"状态的路径。**

### 4.2 结果类型与状态编码

求解入口 `mazeSolve(map, startR, startC, initialKeys)` 返回密封接口 `MazeSolveOutcome`：

| 结果 | 含义 |
|------|------|
| `MazeSolveOutcome.Solved(minMoves, firstDir)` | 可解；`minMoves` 为按键次数（冰面滑行算一步），`firstDir` 为下一步方向（起点即终点时为 null） |
| `MazeSolveOutcome.Unsolvable` | 状态空间内确认无解 |
| `MazeSolveOutcome.TooLarge` | 蜂蜜 / 钥匙 / 锁过多，状态空间过大放弃求解（生成器拒收失败重试，提示返回 TooLarge 文案） |

调用方约定：`mazeMapSolvable` 把 `Solved / TooLarge` 都视为可解（放行）、仅 `Unsolvable` 为 false；`mazeSolveFromState` 仅在 `Solved` 时返回结果，否则 null。

为让 BFS 去重高效且无 GC 压力，把状态打包进一个 `Long`：

```kotlin
fun pack(r, c, keys, honey, keyMask, lockOpen): Long =
    (r.toLong() shl 48) or
        (c.toLong() shl 40) or
        (keys.toLong() shl 36) or
        (honey.toLong() shl 20) or
        (keyMask.toLong() shl 12) or
        lockOpen.toLong()
```

| 段 | 位宽 | 含义 |
|----|------|------|
| `r` | 8 | 行坐标 |
| `c` | 8 | 列坐标 |
| `keys` | 4 | 持有的钥匙数 |
| `honey` | 16 | 已收集蜂蜜的位掩码（每罐一位） |
| `keyMask` | 8 | 已拾取钥匙的位掩码（防重复计数） |
| `lockOpen` | 12 | 已开启锁门的位掩码 |

配套约束：**蜂蜜 ≤ `MAX_SOLVE_HONEY`（10）**、**钥匙 / 锁 ≤ 4**——超过任一项即返回 `TooLarge`，不再进入 BFS。生成器通过 3.3 的预算裁剪保证所有生成关卡都在上限内，`mazeSolve` 能给出精确结果；`TooLarge` 只作为显式容错边界存在。

### 4.3 单步转移 `step()`：冰面滑行 + 事件结算

一次按键（方向 `dr, dc`）被抽象为一次 `step()`，它返回一步或一整套滑行后的新状态（`IntArray` 末位 `1` 表示通关）：

```kotlin
fun step(r0, c0, keys0, honey0, keyMask0, lockOpen0, dr, dc): IntArray? {
    val nr = r + dr
    val nc = c + dc
    if (!walkable(nr, nc, keys, lockOpen)) return null   // 含"持钥可开锁"判定
    r = nr; c = nc
    var sliding = g[r][c] == 'I'                         // 落在冰面则开始滑行
    var guard = 0
    while (true) {
        when (val ch = g[r][c]) {
            'H' -> {
                val idx = honeyIndex[r * cols + c]
                if (idx >= 0) honey = honey or (1 shl idx)
            }
            'K' -> {
                val idx = keyIndex[r * cols + c]
                if (idx >= 0 && (keyMask and (1 shl idx)) == 0) {
                    keyMask = keyMask or (1 shl idx)     // 同一把钥匙只拾取一次
                    keys++
                }
            }
            'L' -> {
                val idx = lockIndex[r * cols + c]
                if (idx >= 0 && (lockOpen and (1 shl idx)) == 0 && keys > 0) {
                    keys--                               // 开锁消耗 1 把钥匙
                    lockOpen = lockOpen or (1 shl idx)
                }
            }
            in '1'..'9' -> {
                val id = ch - '0'
                // 查 portals[id] 配对表，r/c 跳到另一端；sliding = false
            }
            'E' -> if (honey == allHoneyMask) return intArrayOf(r, c, keys, honey, keyMask, lockOpen, 1)
        }
        if (!sliding) break
        val sr2 = r + dr
        val sc2 = c + dc
        if (!walkable(sr2, sc2, keys, lockOpen)) { sliding = false; break }
        r = sr2; c = sc2                                 // 滑行：朝 dr/dc 继续走
        sliding = g[r][c] == 'I'
        if (++guard > rows * cols) break                 // 防死循环兜底
    }
    return intArrayOf(r, c, keys, honey, keyMask, lockOpen, 0)
}
```

注意四点：

- **冰面滑行是"走一步顶多滑到撞墙为止"**，与真实游戏 `MazeGame.tryMove / onStepLanded` 的规则严格对齐，保证校验与玩法一致；
- **锁门消耗机制**：无钥不可进，有钥可进且消耗 1 把、该锁记为开启；
- **钥匙掩码防重复**：`keyMask` 保证同一把钥匙只加一次钥匙数（与真实玩法的"格子变地板"语义一致）；
- **guard 上限**防止异常布局下滑行死循环。

传送门瞬移由 `portals` 索引表（`r*cols+c` 的 Int 编码，避免热循环内 `Pair` 分配）查另一端，并重置 `sliding`。

### 4.4 BFS 主循环

BFS 用 `dist: HashMap<Long, Int>` 记录每个状态的最小步数，并额外用 `firstDir: HashMap<Long, MazeDir>` 记住每个状态**首次到达所走的第一步**——这样找到出口后能把"最小步数"还原成"下一步按哪个方向"，直接支撑提示功能：

```kotlin
val q = ArrayDeque<Long>()
val dist = HashMap<Long, Int>()
val firstDir = HashMap<Long, MazeDir>()
val start = pack(sr, sc, initialKeys, 0, 0, 0)
dist[start] = 0
q.add(start)
while (q.isNotEmpty()) {
    val st = q.removeFirst()
    val steps = dist.getValue(st)
    // 解包 st 得到 (r, c, keys, honey, keyMask, lockOpen)
    if (g[r][c] == 'E' && honey == allHoneyMask) {
        return MazeSolveOutcome.Solved(steps, firstDir[st])
    }
    for (dir in dirs) {
        val next = step(...) ?: continue
        if (next[6] == 1) {
            return MazeSolveOutcome.Solved(steps + 1, firstDir[st] ?: dir)
        }
        val p = pack(next[0], next[1], next[2], next[3], next[4], next[5])
        if (p !in dist) {
            dist[p] = steps + 1
            firstDir[p] = firstDir[st] ?: dir
            q.add(p)
        }
    }
}
return MazeSolveOutcome.Unsolvable
```

`dist` 以打包后的 `Long` 去重，等价于对状态图做 visited 判定。**一旦找到"蜂蜜收齐且位于出口"的状态即返回 `Solved`**；全部状态耗尽仍未达则 `Unsolvable`。

### 4.5 与生成器的联动：重试 + 两级兜底 + 严格预算

`generateMazeLevel` 调用 `mazeSolve`（不再使用 `mazeMapSolvable`）并形成多级安全网：

1. 以 `seed xor (attempt × 0x9E3779B97F4A7C15)` 换种子**最多重试 24 次**，每次 `mazeSolve` 校验，`Solved` 即带严格预算返回；
2. `TooLarge` 直接放行返回（生成器已保证蜂蜜预算，正常不会走到）；
3. 全部失败 → **去掉冰面**（`allowIce = false`，去掉最易造成不可解的滑行机制）再生成并校验；
4. 仍失败 → 退化为 **difficulty = 0 的无锁、无传送门低难度纯迷宫**（DFS 连通图必可解）。

```kotlin
repeat(24) { attempt ->
    val level = generateMazeLevelOnce(
        seed = seed xor (attempt.toLong() * 0x9E3779B97F4A7C15UL.toLong()),
        id = id, difficulty = difficulty, allowIce = true,
    )
    when (val solved = mazeSolve(level.map)) {
        is MazeSolveOutcome.Solved -> return level.withStrictBudget(solved.minMoves)
        MazeSolveOutcome.TooLarge -> return level
        MazeSolveOutcome.Unsolvable -> Unit
    }
}
val fallback = generateMazeLevelOnce(seed xor 0xDEADBEEFL, ..., allowIce = false)
// Solved -> withStrictBudget；TooLarge -> 直接返回；Unsolvable -> 继续
val last = generateMazeLevelOnce(seed xor 0x5EEDF00DL, ..., difficulty = 0, allowIce = false)
```

**严格预算回填 `withStrictBudget`**：生成器算得出精确最小步数时，保证预算是 `minMoves × 1.15`（至少 `minMoves + 1`）；只有算不出最小步数（`TooLarge`）时才放弃该校验。基础预算公式集中在 `MazeGameLogic.moveBudget`（见 9），避免散落多处。

这套"重试 + 降级"策略确保了：**任何种子最终都能产出一个可通关的关卡**，且可解性在源头被强制保证，而不是把不可解关丢给玩家。

## 5. 提示系统

提示功能复用第 4 章的 `mazeSolve`：把**当前**棋盘（已消耗的蜂蜜 / 钥匙 / 已开的锁都已是 `.`）与玩家当前位置、持有钥匙数作为输入，求「收齐剩余蜂蜜并到达出口」的下一步方向。为避免在主线程跑 BFS，UI 侧做成了「主线程抓快照 → 后台求解 → 回主线程校验回写」的异步流水线。

### 5.1 请求与回写

`MazeGame` 提供四个 API：

| 方法 | 作用 |
|------|------|
| `hintRequest()` | 主线程抓取不可变局面快照 `MazeHintRequest(map, bearR, bearC, keys)`；对局不在正常操作态（非 `PLAYING` / 移动中 / 已结算）返回 null |
| `hintRequestMatches(request)` | 校验快照是否仍对应当前局面：阶段 / 位置 / 钥匙一致，且逐格比对字符编码后的棋盘 |
| `applyHint(request, outcome)` | 回写后台结果：快照过期返回 null；`Solved` 且有方向 → `hintsUsed++` 并返回 `MazeHint.Direction`；`Solved` 但 `firstDir == null` / `Unsolvable` → `MazeHint.NoSolution`；`TooLarge` → `MazeHint.TooLarge` |
| `hint()` | 同步版本（直接跑 `mazeSolve` 并计数），供单测与简单场景使用；`MazePlayField` 走的是异步路径 |

`MazeHintRequest` 是 `data class`，`map` 用 `List<String>` 结构相等，因此"内容相同"即视为同一局面——这也是 `MazeHintSession` 缓存判定的基础。

`MazeHint`（UI 结果）与 `MazeSolveOutcome`（求解结果）是两套类型：前者只保留 UI 需要的 `Direction / NoSolution / TooLarge`。

### 5.2 会话状态机 `MazeHintSession`

`MazeHintSession` 只承载提示的会话状态，不依赖 Compose 组合，可在 JVM 单测中直接驱动：

- `busy: Boolean`（Compose `mutableStateOf`）：是否有在途求解；HUD 提示按钮据此**防连点**禁用；
- `cachedFor(request)`：同一局面（`MazeHintRequest` 相等）直接返回上次结果，不重复跑 BFS、不重复计数；
- `begin(request)`：代次 `generation++`，记录请求、清空旧缓存、置 `busy = true`，返回本次代次 token；
- `complete(token, hint)`：仅当 token 等于当前代次才采纳（写缓存、`busy = false`、返回 true）；切关 / 重开后的旧结果因代次不符被丢弃；
- `finish(token)`：任务收尾（含异常路径）仅对当前代次复位 `busy`，旧任务的 `finally` 不会误清新任务的忙碌态；
- `cancel()`：切关 / 重开 / 退出时 `generation++` 让在途任务过期，并立即复位 `busy` 与缓存，避免按钮一直禁用到旧 BFS 结束。

### 5.3 UI 装配：后台求解 + 主线程校验

`MazePlayField` 把上述状态机接到 UI 上（`onHint` 回调）：

```kotlin
val hintSession = remember(game.boardVersion) { MazeHintSession() }
LaunchedEffect(game.boardVersion) {          // 换关 / 重开 / 撤销：取消在途求解并清提示 UI
    hintJob?.cancel()
    hintJob = null
    clearHintUi()
}
...
val token = hintSession.begin(request)
hintJob = scope.launch {
    try {
        val outcome = withContext(Dispatchers.Default) {          // 纯 BFS 在后台线程
            mazeSolve(request.map, request.bearR, request.bearC, request.keys)
        }
        val hint = game.applyHint(request, outcome)               // 回主线程：校验快照 + 计数
        if (hint != null && hintSession.complete(token, hint)) {
            showHint(hint)                                        // 箭头 / 无解 / 暂不支持横幅
        }
    } finally {
        hintSession.finish(token)
    }
}
```

要点：

- **后台执行**：`mazeSolve` 是纯函数，`withContext(Dispatchers.Default)` 里只做计算，不碰 Compose 状态；
- **回主线程双重校验**：`applyHint` 先用 `hintRequestMatches` 验证快照（棋盘 / 位置 / 钥匙 / 阶段），`MazeHintSession.complete` 再用代次验证；任一层失败都丢弃结果；
- **同局面缓存**：点击时先 `cachedFor(request)`，命中则直接展示缓存方向，不发起新任务；
- **防连点**：`busy` 期间按钮不可用（`MazeHudTopBar` 的 `hintBusy` 参数）；
- **展示**：方向由 `drawMazeHint` 在目标格画脉动箭头并高亮 D-pad；无解 / 状态空间过大会显示 `MazeHintBanner` 文案，均 `HINT_HIGHLIGHT_MS = 1500L` 后自动消失；
- **任何一次移动 / 撤销都会先 `clearHintUi()`**，提示不会跨局面残留。

### 5.4 `hintsUsed` 计数语义

- `hintsUsed` 是 `MazeGame` 的 Compose 状态，`loadLevel` 时归零，并随 `MazeSession.hintsUsed` 落盘 / 恢复（见 `MazeGameSessionTest.restoreSession_roundTripsHintsUsed`）；
- 只有**成功给出方向**（`Solved` 且 `firstDir != null`）才 +1；`NoSolution` 与 `TooLarge` 都不计数；
- `applyHint` 自身**不去重**：内容相同的快照重复回写会各计一次；正常路径由 `MazeHintSession.cachedFor` 拦截同局面重复请求，因此同一局面至多计一次；
- 结算卡片在 `hintsUsed > 0` 时展示"使用提示 n 次"。

## 6. 渲染与性能

渲染拆成"静态烘焙层 + 逐帧动态层"两条路径：不随时间变化的部分只在关卡 / 画布变化时画一次，之后每帧只 `drawImage`；会动的部分按需逐格绘制，且不在热路径分配 `Path / Brush`。

### 6.1 分层与帧循环

`MazePlayField` 是对局装配层：`Canvas` 的 draw lambda 里只读 `frame.value`（每帧变化的 `Long`），从而只让**绘制阶段**失效、不触发整个 Composable 重组。`drawMazeWorld` 的绘制顺序：

1. `drawThemeMotes`（主题氛围微粒，画在棋盘背后）；
2. **静态底层**：命中 `MazeBaseLayerCache` 就一次 `drawImage`，否则回退 `drawMazeBoardCells` 逐格绘制；
3. 逐格动态叠加 `drawMazeTileOverlay`（蜂蜜 / 冰面 / 钥匙 / 锁 / 传送门 / 出口 / 起点）；
4. `drawPortalMotes`、`drawExitGlow`、`drawMazeHint`、`drawIceTrail`、`drawPortalGhost`、`drawUnlockGhost`；
5. 事件粒子 `MazeFxHost.drawParticles`（`reduceMotion` 时整段跳过）；
6. 小熊 `drawMazeBear`（呼吸 / 滑行 / 落地 / 回弹 / 传送 / 庆祝 / 垂头）。

静态层与动态层共用同一份 `mazeBoardLayout` 坐标，保证两层像素对齐。

### 6.2 静态层烘焙 `MazeBaseLayerCache`

- **烘焙内容**：`drawMazeBaseLayer` = 场景装饰（`drawMazeSceneDecor`）+ 棋盘投影 + 全部墙 / 地板（`drawMazeBoardCells`）+ 外框（`drawBoardRim`）与暗角（`drawBoardVignette`）；
- **2 槽 LRU**（`MAX_ENTRIES = 2`）：命中时把该槽移到队尾；未命中时**先淘汰最旧槽位再分配**，因此峰值同时只驻留 2 张全屏位图（新 + 1 旧）；
- **缓存键**：量化后的尺寸 `w/h`、关卡身份（缓存项 `e.level === level`，引用相等）、主题样式（`e.style == style`，数据类相等）、顶部 / 底部系统栏预留 px（`topReservePx` / `bottomReservePx`）；任一项变化才重烘；
- **4px 量化**：`quantizeBitmapPx` 把画布尺寸向上取整到 4px 网格（`(ceil + 3) / 4 * 4`），分屏拖拽时的亚像素抖动不再触发反复重烘；缓存键、烘焙尺寸与动态层布局共用同一量化值；
- **失败降级**：`ImageBitmap` 分配或烘焙包在 `runCatching` 中，失败返回 null，由 `drawMazeWorld` 回退到逐格绘制，不影响玩法；
- **采样**：`drawImage(..., filterQuality = FilterQuality.None)`，位图与屏幕像素 1:1 对齐；撞墙轻抖通过 `dstOffset` 偏移整张缓存图实现。

HUD 预留常量与布局算法在 `MazeThemeArt.kt`：`MAZE_HUD_TOP_DP = 96f`、`MAZE_HUD_BOTTOM_DP = 230f`、`MAZE_MIN_AVAIL_H_FRACTION = 0.40f`；`mazeEffectiveReserves` 在低高度窗口（横屏 / 分屏）按比例裁剪预留，保证棋盘可用高度不低于画布的 40%，`mazeBoardLayout` 返回 `MazeBoardLayout(cell, ox, oy)`。

### 6.3 主题美术：`MazeThemeArt` / `MazeThemeDecor`

`MazeTheme` 共六个主题（`GARDEN / RAIN / SNOW / NIGHT / FESTIVAL / CLOUD`），`mazeThemeStyle` 给出 `MazeThemeStyle` 配色。静态层按主题选择墙 / 地纹理：

| 主题 | 墙 | 地板 |
|------|----|------|
| `GARDEN` | `drawWoodWall` 木篱笆横板 + 木纹 + 苔藓 | `drawGrassFloor` 草叶 + 概率小花 |
| `RAIN` | `drawBrickWall(wet = true)` 错缝石砖 + 墙面雨痕 | `drawStoneFloor` 石缝 + 水洼 |
| `SNOW` | `drawSnowWall` 石基 + 积雪顶盖 + 冰棱 | `drawSnowFloor` 雪点 + 雪花 |
| `NIGHT` | `drawNightWall` 深色砖石 + 微光符文点 | `drawNightFloor` 暗砖缝 + 星光点 |
| `FESTIVAL` | `drawLanternWall` 红墙金边 + 挂灯笼 | `drawCarpetFloor` 红毯金纹 |
| `CLOUD` | `drawCloudWall` 蓬松云块 | `drawCloudFloor` 云朵圆斑 |

纹理位置全部由 `mazeHash01(i, salt)` 确定性伪随机派生（同一格永远同值，不随帧抖动）；`mazeLighten / mazeDarken` 做明暗；`mazeStroke(width)` 用 A/B 双槽复用 `Stroke`，动态层热路径不 new。

`MazeThemeDecor` 负责棋盘外围的场景装饰（`drawMazeSceneDecor`），随静态层一起烘焙、无时间参数：花园太阳 / 远山 / 花丛、雨巷云 / 伞 / 水洼、雪林雪堆 / 松树（`drawPine`）、夜空 54 颗星 / 弯月 / 远山、节日灯笼串 / 角旗 / 静态烟花（`drawLantern`）、云端云团 / 彩虹 / 小鸟，以及公共的 `drawSceneBackdrop` 柔光与地面投影带。

### 6.4 动态叠加：`MazeOverlays`

`drawMazeTileOverlay` 按 `MazeTile` 分派逐帧绘制：

- **蜂蜜**：罐体 / 木盖 / 玻璃高光，呼吸缩放与星光闪烁（`reduceMotion` 下静止）；
- **冰面**：半透明冰面 + 确定性裂缝折线 + 高光；
- **钥匙**：钥匙环 / 键杆 / 齿口，上下浮动（`reduceMotion` 下静止）；
- **锁门**：木门 + 铁箍 + 锁片钥匙孔 + 链条，未开锁时锁片微颤（`reduceMotion` 下冻结）；
- **传送门**：分段落旋转外环 + 反向内环 + 中心旋涡 + 门号色点，`portalId % 3` 决定色带；
- **出口**：拱门石柱 + 随 `doorOpenProgress` 上滑收起的门扇；全开时门洞亮光与上升粒子（`reduceMotion` 下门相位冻结为全开静态）；
- **起点**：地垫 + 小熊爪印，站在起点时地垫发亮；
- 另有 `drawMazeHint`（提示脉动箭头）、`drawPortalGhost`（传送出发点收束环）、`drawUnlockGhost`（开锁瞬间碎门残影），后两者 `reduceMotion` 直接不画。

性能约定：不创建 `Path / Brush`，只用 `drawRect / drawCircle / drawArc / drawLine` 组合，`mazeStroke` 复用共享 `Stroke`；所有动效由 `game.time` 驱动，确定性且不依赖帧率。

### 6.5 粒子与特效：`MazeParticles`

`MazeFxHost` 是事件特效宿主（拾取 / 开锁 / 传送 / 通关等爆发粒子 + 小熊演出标记 + 撞墙屏幕轻抖）：

- **环形池**：并行 `FloatArray`（`pX/pY/pVx/pVy/pG/pBorn/pLife/pSize`）+ `IntArray`（`pKind/pColor`），容量 `CAP = 192`，游标 `cursor` 回绕覆盖最旧粒子，不产生每帧大对象；
- **粒子种类**：`KIND_DOT / KIND_STAR / KIND_SHARD / KIND_DEBRIS / KIND_CONFETTI / KIND_RING / KIND_DUST`，随机量全部由 `mazeHash01` 从自增序号派生，事件确定可复现；
- **`compact(time)`**：原地把存活粒子搬到数组前段，并把 `cursor` 同步到 `count % CAP`——否则环形回绕会覆盖仍存活的粒子；`liveCount(time)` 统计存活数；
- **状态观测 `observe(game, style)`**：在绘制阶段只读对局状态做边沿检测（`prevGrid` 身份变化时清空池、蜂蜜减少 / 钥匙增减 / 传送 / 通关 / 移动拖尾），不改玩法状态；`setTrailDir` 供绘制小熊前写入朝向；
- **`isIdle(game)`**：通关庆祝已结束且无存活粒子时返回 true；通关但庆祝尚未被 `observe` 观测时先返回 false，避免帧循环抢在首帧绘制前暂停；
- **氛围微粒 `drawThemeMotes`**：按主题确定性时间驱动（花园 14 / 雪 12 / 夜 10 / 节日 16 / 云 6 / 雨 10 枚），`reduceMotion` 直接不画；
- 其余动态特效：`drawIceTrail`（冰面滑行拖尾）、`drawPortalMotes`（传送门吸入 / 吐出微粒）、`drawExitGlow`（出口光晕呼吸，开门后增强）在 `reduceMotion` 下均跳过或降级为静态。

### 6.6 HUD：`MazeHud`

- **`MazeHudTopBar`**：主题胶囊（`mazeThemeGlyph` + 标题）+ 一排玻璃圆钮（关闭 / 撤销 / 提示 / 重来 / 暂停 / 角色），按钮用 `MazeGlassButton`（38dp 圆钮、主题渐变 + 描边、禁用降透明度）；提示按钮的 `enabled = phase == PLAYING && !moving && !hintBusy`；第二行为 `MazeChip` 芯片（蜂蜜进度 / 钥匙数 / 步数预算，带 `LinearProgressIndicator`，超预算 `warn` 变红）；
- **`MazeDPad`**：木质爪印方向键，`MazePadKey` 按下缩放（`animateFloatAsState` + 无涟漪 `clickable`），`highlightDir` 在提示时高亮下一步方向；移动中整体禁用，滑动操作仍由画布手势处理；
- **`MazeHintBanner`**：底部主题横幅，承载"还差蜂蜜 / 无解 / 暂不支持提示"三类文案；
- **`MazeResultOverlay`**：结算卡片（星级 / 步数 / 提示次数 / 失败详情），`MazeStarRow` 逐个点亮星星；`reduceMotion` 时星星直接全亮、不播 delay 动画。遮罩吞掉所有指针事件，避免点击穿透棋盘。

### 6.7 `boardVersion` 驱动的提示清理

`MazeGame.boardVersion` 在 `loadLevel`（换关 / 重开）与 `undo` 时自增（普通移动不自增），语义是"棋盘或位置被重置"。对局页用它做两件事：

1. `val hintSession = remember(game.boardVersion) { MazeHintSession() }`——棋盘代次变化直接换一个全新会话，旧缓存作废；
2. `LaunchedEffect(game.boardVersion) { hintJob?.cancel(); clearHintUi() }`——取消在途 BFS 并清掉三类提示 UI，旧结果不会残留到新棋盘。

选关页的进度复制则用另一个版本号 `progressVersion`（星级 / 解锁变化时自增）做 `remember` key。

### 6.8 `reduceMotion` 覆盖与结算停帧

全局设置 `LocalReduceMotion` 会被对局与选关共同读取，覆盖范围：

- **粒子 / 天气**：事件粒子、主题氛围微粒、冰面拖尾、传送门微粒不画；天气覆盖层只保留静态天色；
- **小熊演出**：撞墙回弹、拾取上跳、落地挤压、静止呼吸、传送旋入、通关庆祝、失败垂头全部关闭（通关时用静态落地帧）；
- **格子动效**：蜂蜜呼吸 / 星光、钥匙浮动、锁片微颤、传送门旋转、提示脉动全部冻结为静态相位；出口门相位固定为全开；
- **选关页**：`MazeLevelSelect` 的云漂移 `drift` 与"下一关"脉冲 `pulse` 不再启动无限动画，固定为 0；
- **结算**：`MazeStarRow` 不做延时点亮，直接展示最终星级。

**结算阶段帧循环暂停**：`BearMazeScreen` 的 `GameFrameLoop(paused = ...)` 在"弹窗 / 角色选择 / 选关阶段 / 暂停 / `CLEAR && fx.isIdle(game)`"时停帧。`isIdle` 会等通关庆祝被首帧观测且粒子全部过期后才为 true，因此庆祝动画能完整播放，播完即停帧省电。

## 7. 算法复杂度分析

### 7.1 生成器

- **DFS 雕刻**：每个格至多访问一次，`O(rows × cols)`。
- **BFS 求距离**：`O(rows × cols)`。
- **元素摆放**：在 `open` 池（≤ 格数）上做常数次线性扫描，`O(rows × cols)`。
- 总体：`O(n)`，`n = rows × cols`（单次尝试）；可解性校验见 7.2。

### 7.2 可解性判定（状态 BFS）

- 状态空间大小 `≤ rows × cols × 2^keys × 2^honey × 2^locks`。
- 每状态 4 个方向的转移，每次 `step` 冰面最多滑 `rows × cols` 步（有 guard 兜底）。
- 因此最坏 `O(rows × cols × 4 × 状态数 × 滑行上限)`。**状态数随蜂蜜 / 钥匙指数增长**——这正是 4.2 用位掩码 + 上限（蜂蜜 ≤ 10、钥匙 / 锁 ≤ 4）的原因，也是"超过上限即 `TooLarge`"的合理性所在。

**实际规模**：生成器保证蜂蜜 ≤ `MAX_SOLVE_HONEY`（10）、钥匙 / 锁 ≤ 4、传送门 ≤ 3 对；`MazeSolvabilityTest.generatedHardLevels_honeyWithinSolveBudget_neverTooLarge` 对高难无尽波次断言永远不返回 `TooLarge`，因此生成路径总能拿到精确最小步数。

## 8. 正确性与健壮性保障

1. **单一事实来源**：`MazeSolvability.step` 与 `MazeGame.tryMove / onStepLanded` 对冰面 / 钥匙 / 锁 / 传送门的语义逐一对齐，避免"校验说可解、玩法却卡住"的不一致；`MazeGameLogic.simulateIceStep` 提供第三份可单测的滑行模拟。
2. **生成后强校验**：每一关在返回前都经过 `mazeSolve` 判定并回填严格预算，杜绝不可解关与"可解但预算不够"入库。
3. **显式容错边界**：状态空间过大返回 `TooLarge`；滑行有 guard；找不到钥匙位就撤回；静态层位图分配 / 烘焙失败回退逐格绘制。多处"宁可放弃也不要出错"。
4. **可单测**：`mazeSolve / generateMazeLevel / MazeHintSession` 等为纯函数或纯状态机（`internal` 可见性即为测试而设），`MazeGameLogic` 与 Compose / Android 完全解耦。

## 9. 与真实游玩的衔接

- **战役**：手写 12 关 + 种子生成 48 关（共 `MAZE_CAMPAIGN_SIZE = 60`），生成关难度 ≈ 关卡下标，同一关永远同一张图。
- **无尽模式**：每波用 `cachedEndlessLevel(会话种子, 波次, 难度)` 生成新图，难度 `MazeGameLogic.endlessDifficulty` = `8 + 2×波次`（封顶 45）；重开（`freshSeed = false`）复用会话种子保证同一图；超步即 `failEndless`（结算失败、不更新最高波次）。
- **每日迷宫**：`dailyMazeLevel(dateEpochDay)` 按本地日派生确定性布局，固定难度 14，同一天多次进入完全一致，便于横向比较成绩。
- **步数预算与星级**：基础预算 `MazeGameLogic.moveBudget(shortestPathLen, honeyCount, difficulty) = 最短路 × 2.2 + 蜂蜜数 × 6 + 难度 × 2`（最短路至少按 8 计，结果截断在 `30..220`）；生成器再用 `withStrictBudget` 保证 `minMoves × 1.15`（至少 +1）。结算 `MazeGameLogic.starsFor`：`moves ≤ budget` 3 星、`≤ budget × 1.35` 2 星、否则 1 星。
- **撤销与提示**：`MazeGame` 维护上限 `UNDO_LIMIT = 30` 的快照历史（棋盘深拷贝），撤销/换关自增 `boardVersion`；提示计数 `hintsUsed` 随 `MazeSession` 落盘。
- **进程恢复**：把含元素状态与玩家状态的棋盘序列化（`MazeSession`，键 `MAZE_SESSION_KEY = "maze_session_v1"`）落盘，旋转屏幕 / 杀进程后可无缝恢复对局；选关阶段不清档，只有主动开新局 / 放弃（`abandonSession`）或结算（CLEAR）才清档。
- **公共层**：局中会话的 `ON_STOP`/`onDispose` 落盘、退出抑制与 CLEAR 清档已统一由 `:game:common` 的 `GameSnapshotLifecycle`（`GameSnapshotSession.kt`）驱动（`restoreOnEnter = false`，保持「进入先回选关、点『继续』才恢复」的交互）；`GameCards.kt`（公共 READY/结算卡）与 `GameRenderPrimitives.kt`（`BakedLayerLru`/`strokeOf`/`gameHash01` 渲染原语）供各游戏复用。

## 11. 可能的改进方向（供后续迭代）

1. **状态编码扩容**：若未来想支持更多钥匙 / 蜂蜜，需扩位宽或改用 `Long` 之外的高位 / 哈希状态表示（如把蜂蜜掩码换成 `BitSet`），并同步放宽 `MAX_SOLVE_HONEY` 与钥匙 / 锁上限。
2. **种子 replay 测试**：固定种子集对"每种难度批量生成并断言 100% 可解"，可作为回归测试，量化不同难度下的重试 / 兜底频率与状态空间规模（现有 `MazeSolvabilityTest` 已覆盖一部分）。
3. **提示预取**：目前提示按需后台求解；可在关卡开始时按当前局面预跑一次 BFS 或用 `firstDir` 缓存整条最短路径，进一步降低点击延迟。
4. **静态层扩展**：把冰面 / 起始点地垫等"只随棋盘变化"的元素也纳入 `MazeBaseLayerCache` 烘焙，进一步减少逐帧绘制量（需权衡缓存键与烘焙耗时）。
5. **引擎 / UI 解耦**：`MazeGenerator`、`MazeSolvability` 与 `MazeGameLogic` 可独立为无 Android 依赖的纯 Kotlin 库，便于脱离 UI 做算法基准测试。
6. **难度实证**：统计 `difficulty` 递增时生成成功率、平均状态数、平均重试次数，形成难度曲线数据（可直接用于毕设实验章节）。
