# 迷宫生成与可解性算法技术说明

> 对应模块：`:game:maze`（小熊迷宫）
> 核心文件：`MazeGenerator.kt`、`MazeSolvability.kt`、`BearMazeScreen.kt`
> 摘要：本文说明小熊迷宫如何用「递归回溯雕刻」生成迷宫，如何在生成后叠加蜂蜜 / 冰面 / 钥匙锁 / 传送门四类玩法元素，以及如何用「带约束的状态空间 BFS」保证每一关都可解、无死锁。

---

## 1. 背景与问题定义

小熊迷宫是一个以"小熊"为主角的推箱子式 2D 迷宫游戏。与常见走迷宫不同，它引入了四类**改变可达性语义**的格子：

| 格子 | 符号 | 语义 |
|------|------|------|
| 地板 | `.` | 可通行 |
| 墙 | `#` | 不可通行 |
| 起点 | `S` | 玩家初始位置 |
| 出口 | `E` | 通关目标；**需先收齐全部蜂蜜**才可离开 |
| 蜂蜜 | `H` | 收集物；未收集齐时出口关闭 |
| 冰面 | `I` | 进入后**沿当前方向持续滑行**，直到撞墙/撞不可通行格 |
| 钥匙 | `K` | 拾取后钥匙数 +1 |
| 锁门 | `L` | 需消耗 1 把钥匙才能通过（用后即开，不再消耗） |
| 传送门 | `1`–`9` | 同号成对，踩上即瞬移到另一端 |

**核心难点**：因为冰面的"滑行"会让玩家无法随意停在任一格、锁门会消耗钥匙、传送门会改变拓扑，所以**"这张迷宫图能不能通关"不再是一个普通 BFS 能直接回答的问题**。程序生成的关卡必须保证：

1. **可通关**（存在一条合法路径走到出口且收齐全部蜂蜜）；
2. **无死锁**（钥匙出现在锁门的"起点侧"，玩家不至于因拿不到钥匙而必然卡死）；
3. **有难度梯度**（越高难越复杂、元素越多，但始终可解）。

---

## 2. 迷宫图建模

关卡用字符网格表示，`MazeLevel.map: List<String>`，行/列数由内容决定（`rows`、`cols` 通过 `parse()` 转为二维 `MazeCell` 数组）。这样的好处是：

- **人类可读、可手写**：前 12 关就是手工用字符画出来的教程关；
- **可序列化**：整局棋盘可编码成字符串，用于进程重建时恢复对局（`MazeSession`）；
- **纯数据、无 Android 依赖**：生成器与可解性判定都是纯 Kotlin 函数，便于单元测试。

```text
###########
#S....H...#
#.###.###.#
#...#...#.#
###.#.#.#.#
#...#.#...#
#.###.#####
#.....H..E#
###########
```

`MazeLevel.parse()` 与 `MazeGame` 中的 `tileToChar / charToCell` 使用同一套字符集，保证"生成 → 落盘 → 恢复"三处编码一致。

## 3. 迷宫生成算法

### 3.1 结构骨架：递归回溯（DFS 雕刻）

生成器采用经典的**递归回溯（Recursive Backtracking）**迷宫算法：

1. 棋盘初始全为墙 `#`，尺寸取**奇数**（如 `11–21` 列、`9–19` 行，随难度增长）。
2. 从 `(1,1)` 起落脚，每次向四个方向**隔一格**（步长 2）探索，只要目标格是墙就打穿中间的格并递归。
3. 通过洗牌（shuffle）随机化探索顺序，产生不同迷宫形态。

```kotlin
val dr = intArrayOf(-2, 2, 0, 0)
val dc = intArrayOf(0, 0, -2, 2)

fun dfs(r: Int, c: Int) {
    carve(r, c)
    val order = intArrayOf(0, 1, 2, 3).also { it.shuffle(rng) }
    for (i in order) {
        val nr = r + dr[i]; val nc = c + dc[i]
        if (nr in 1 until rows - 1 && nc in 1 until cols - 1 && g[nr][nc] == '#') {
            carve(r + dr[i] / 2, c + dc[i] / 2)   // 打通两格之间的墙
            dfs(nr, nc)
        }
    }
}
```

奇偶格策略保证所有通道宽度为 1，是"完美迷宫"（无环、任意两格间路径唯一）的典型构造。

### 3.2 出口选择：BFS 距离取最远格

为让关卡有"走到对面"的目标感，生成后跑一次 **BFS**，把**距离起点最远的可达格**设为出口 `E`：

```kotlin
val distFromStart = bfsDist(start)          // 每个格子到起点的最短距离
var exit = start; var best = -1
for ((r, c) in 所有格) if (distFromStart[r][c] > best) { best = ...; exit = r to c }
g[exit] = 'E'
```

这一步同时得到了 `distFromStart`——后续摆放元素时用它来施加空间约束。

### 3.3 元素摆放与难度参数化

生成器按 `difficulty`（战役关≈关卡下标，无尽关≈波次换算）平滑解锁各元素，所有元素只落在"可达且非起点附近"的地板格（`open` 池，已按 BFS 距离过滤）：

| 元素 | 出现条件 | 数量 | 关键约束 |
|------|----------|------|----------|
| 蜂蜜 `H` | 始终 | `2 + difficulty/4`，`2..10` | 随机地板格 |
| 冰面 `I` | `difficulty ≥ 2` | `3 + difficulty/3`，`3..18` | 避开起点紧邻（`dist ≤ 2`） |
| 钥匙 `K` + 锁 `L` | `difficulty ≥ 4` | 1 组；`≥10` 时第 2 组 | 见 3.4 |
| 传送门 `1-9` | `difficulty ≥ 6` | `1 + (difficulty-6)/8`，`1..3` 对 | 成对出现 |
| 捷径 | `difficulty ≥ 8` | `2 + difficulty/15` | 随机在两面邻通的墙上开洞 |

### 3.4 防死锁的"钥匙-锁"调度

这是生成器里最有设计含量的一部分。普通随机放钥匙/锁很容易产生**不可解关**（锁挡住了唯一通路，而钥匙在锁的"出口侧"永远够不到）。生成器用三条规则规避：

1. **锁放在唯一通路**：只选**真死胡同**（`openNeighborCount == 1`，只有唯一开放邻格）作为被锁住的蜂蜜位置，锁放在其**唯一通向处**，使"关蜂蜜的锁"无法被从旁绕开；
2. **钥匙必须落在锁的起点侧**：钥匙的 `distFromStart < 锁的 distFromStart`（`d in 2 until lockDist`），保证玩家**必须先经过钥匙、才能到达锁**；
3. **找不到安全钥匙位就整体撤回**——锁必须落在唯一通路上，钥匙必须落在起点侧：

```kotlin
val keySpot = open.firstOrNull { (r, c) ->
    val d = distFromStart[r][c]
    d in 2 until lockDist.coerceAtLeast(3)   // 钥匙须在锁的起点侧
} ?: open.firstOrNull { (r, c) -> distFromStart[r][c] in 1 until lockDist }

if (keySpot != null) { open.remove(keySpot); g[keySpot] = 'K' }
else { /* 撤回：锁位和蜂蜜位恢复为地板 */ }
```

"宁缺毋死锁"——如果当前随机布局配不出合法的钥匙位，就撤销这一组，而不是硬着头皮产出一个必然卡死的关。

### 3.5 种子可复现

每个战役关由固定种子生成，**同一关永远同一张图**：

```kotlin
val seed = 0xBEEF0000L xor (i.toLong() * 0x9E3779B9L)
```

`0x9E3779B9`（黄金比例相关常数）用于把下标扩散成不相关的种子。这带来三个好处：关卡唯一可标识、便于调试复现、无尽模式的"重开同一图"语义（`freshSeed=false` 复用时序种子）。

## 4. 可解性判定：带约束的状态空间 BFS

### 4.1 为什么普通 BFS 不够

若迷宫只有墙和地板，用一次 BFS 即可判断可达性。但引入**蜂蜜需求、冰面滑行、钥匙消耗、传送门瞬移**后，"能不能通关"取决于**路径选择**，而不只是连通性：

- 明明物理可达，但**没收集齐蜂蜜** → 出口打不开；
- 冰面上**想停停不住** → 能到达的格子集合与"普通走法"不同；
- 钥匙/锁耦合 → 是否持钥、是否已开锁影响后续可达集合；
- 传送门 → 拓扑变化，且可形成捷径。

因此问题转化为：**在状态图 `(位置, 钥匙数, 蜂蜜掩码, 已开锁掩码)` 上搜索是否存在一条能访问到"收齐蜂蜜后的出口"状态的路径。**

### 4.2 状态编码：64 位位运算打包

为让 BFS 去重高效且无 GC 压力，把状态打包进一个 `Long`：

```kotlin
fun pack(r, c, keys, honey, keyMask, lockOpen): Long =
    (r.toLong() shl 48) or
        (c.toLong() shl 40) or
        (keys.toLong() shl 36) or
        (honey.toLong() shl 20) or
        (keyMask.toLong() shl 12) or
        lockOpen.toLong()
```

| 段 | 位宽 | 含义 |
|----|------|------|
| `r` | 8 | 行坐标 |
| `c` | 8 | 列坐标 |
| `keys` | 4 | 持有的钥匙数 |
| `honey` | 16 | 已收集蜂蜜的位掩码（每罐一位） |
| `keyMask` | 8 | 已拾取钥匙的位掩码 |
| `lockOpen` | 12 | 已开启锁门的位掩码 |

配套约束：**蜂蜜 ≤ 10**（16 位掩码装得下）、**钥匙/锁 ≤ 4**（4/12 位装得下）——与生成器数量上限一致，保证不溢出。状态空间过大时（如蜂蜜 > 12、钥匙 > 4）直接放行（`return true`），避免生成卡死，属于显式容错。

### 4.3 单步转移 `step()`：冰面滑行 + 事件结算

一次按键（方向 `dr, dc`）被抽象为一次 `step()`，它返回一步或一整套滑行后的新状态：

```kotlin
fun step(r0, c0, keys0, honey0, keyMask0, lockOpen0, dr, dc): IntArray? {
    // 1) 目标格可走（含"持钥可开锁"判定）
    if (!walkable(nr, nc, keys, lockOpen)) return null
    // 2) 进入目标格；若为冰面则持续沿方向滑行
    var sliding = g[r][c] == 'I'
    while (true) {
        when (g[r][c]) {
            'H' -> honey |= 1 shl idx          // 收集蜂蜜
            'K' -> keys++                       // 拾取钥匙
            'L' -> if (keys > 0) { keys--; lockOpen |= ... }  // 开锁
            '1'..'9' -> 瞬移到配对传送门         // 传送门
            'E' -> if (honey == allHoneyMask) return 通关
        }
        if (!sliding) break
        // 滑行：朝 dr/dc 继续走，直到下一格不可通行
        if (!walkable(next)) { sliding = false; break }
        前进; sliding = g[newR][newC] == 'I'
        if (++guard > rows * cols) break        // 防死循环兜底
    }
    return 新状态
}
```

注意三点：
- **冰面滑行是"走一步顶多滑到撞墙为止"**，与真实游戏 `MazeGame.onStepLanded()` 的规则严格对齐，保证校验与玩法一致；
- **锁门消耗机制**：无钥不可进，有钥可进且消耗 1 把、该锁记为开启；
- **guard 上限**防止异常布局下滑行死循环。

### 4.4 BFS 主循环

```kotlin
val q = ArrayDeque<Long>(); val seen = HashSet<Long>()
q.add(start); seen.add(start)
while (q.isNotEmpty()) {
    val st = q.removeFirst()
    // 解包 st 得到 (r, c, keys, honey, keyMask, lockOpen)
    if (到达出口且蜂蜜收齐) return true
    for (4 个方向) {
        val next = step(...) ?: continue
        if (通关) return true
        if (seen.add(pack(next))) q.add(pack(next))
    }
}
return false
```

`seen` 以打包后的 `Long` 去重，等价于对状态图做 visited 判定。**一旦找到"蜂蜜收齐且位于出口"的状态即返回 true**；全部状态耗尽仍未达称为不可解。

### 4.5 与生成器的联动：重试 + 两级兜底

`generateMazeLevel` 调用 `mazeMapSolvable` 并形成多级安全网：

1. 以 `seed xor attempt` 换种子**最多重试 24 次**，每次校验可解性，可解即返回；
2. 全部失败 → **去掉冰面**（去掉最易造成不可解的滑行机制）再生成并校验；
3. 仍失败 → 退化为**无锁、无传送门的低难度纯迷宫**（DFS 连通图必可解）。

```kotlin
repeat(24) { attempt -> /* 生成（含冰面）并校验，可解即返回 */ }
val fallback = generate(allowIce = false)      // 兜底 1：去冰面
if (solvable(fallback)) return fallback
return generate(difficulty = 0)                // 兜底 2：低保真必可解
```

这套"重试 + 降级"策略确保了：**任何种子最终都能产出一个可通关的关卡**，且可解性在源头被强制保证，而不是把不可解关丢给玩家。

## 5. 算法复杂度分析

### 5.1 生成器

- **DFS 雕刻**：每个格至多访问一次，`O(rows × cols)`。
- **BFS 求距离**：`O(rows × cols)`。
- **元素摆放**：在 `open` 池（≤ 格数）上做常数次线性扫描，`O(rows × cols)`。
- 总体：`O(n)`，`n = rows × cols`（单次尝试）。

### 5.2 可解性判定（状态 BFS）

- 状态空间大小 `≤ rows × cols × 2^keys × 2^honey × 2^locks`。
- 每状态 4 个方向的转移，每次 `step` 冰面最多滑 `rows × cols` 步（有 guard 兜底）。
- 因此最坏 `O(rows × cols × 4 × 状态数 × 滑行上限)`。**状态数随蜂蜜/钥匙指数增长**——这正是 `4.2` 用位掩码+上限的原因，也是"状态过大即放行"的合理性所在。

**实际规模**：战役关蜂蜜 ≤ 10、钥匙 ≤ 2（双锁关）、传送门 ≤ 3 对，状态空间在可接受的几十万量级内；无尽高难度关可能逼近上限而走快速放行分支。

## 6. 正确性与健壮性保障

1. **单一事实来源**：`MazeSolvability.step` 与 `MazeGame.tryMove/onStepLanded` 对冰面/钥匙/锁/传送门的语义逐一对齐，避免"校验说可解、玩法却卡住"的不一致。
2. **生成后强校验**：每一关在返回前都经过可解性判定，杜绝不可解关入库。
3. **显式容错边界**：状态空间过大直接放行；滑行有 guard；找不到钥匙位就撤回。三处"宁可放弃也不要出错"。
4. **可单测**：`mazeMapSolvable` 与 `generateMazeLevel` 为纯函数，`internal` 可见性即为测试而设。

---

## 7. 与真实游玩的衔接

- **无尽模式**：每波用 `会话种子 xor 波次常数` 生成新图，难度 `8 + 2×波次`（封顶 45）；重开复用会话种子保证同一图。
- **步数预算与星级**：`budget = 最短路 × 2.2 + 蜂蜜数 × 6 + 难度 × 2`，按实际步数给 1–3 星，把"最优路径"概念落地成可感知的挑战。
- **进程恢复**：把含元素状态与玩家状态的棋盘序列化（`MazeSession`）落盘，旋转屏幕/杀进程后可无缝恢复对局。

## 8. 可能的改进方向（供后续迭代）

1. **状态编码扩容**：若未来想支持更多钥匙/蜂蜜，需扩位宽或改用 `Long` 之外的高位/哈希状态表示（如把蜂蜜掩码换成 `BitSet`），并同步放宽 `4.2` 的数量上限。
2. **种子 replay 测试**：固定种子集对"每种难度批量生成并断言 100% 可解"，可作为回归测试，量化不同难度下的重试/兜底频率与状态空间规模。
3. **引擎/UI 解耦**：`MazeGenerator` 与 `MazeSolvability` 可独立为无 Android 依赖的纯 Kotlin 库，便于脱离 UI 做算法基准测试。
4. **难度实证**：统计 `difficulty` 递增时生成成功率、平均状态数、平均重试次数，形成难度曲线数据（可直接用于毕设实验章节）。
