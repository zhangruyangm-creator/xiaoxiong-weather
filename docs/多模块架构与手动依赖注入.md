# 多模块架构与手动依赖注入技术说明

> 对应模块：`:app`、`:core:*`、`:feature:*`、`:game:*`
> 核心文件：`app/src/main/java/com/xiaoxiong/weather/di/AppContainer.kt`、`core/data/.../WeatherPorts.kt`、`game/api/.../GameEntry.kt`、`app/build.gradle.kts`
> 相关文档：`MODULARIZATION.md`（重构设计与迁移过程）、`docs/网络层拦截器缓存与离线降级.md`、`docs/天气数据管线与物候映射.md`、`docs/小熊跳跳2D物理引擎与帧渲染.md` 等
> 摘要：本文从小熊天气的多模块结构出发，说明它的 Clean Architecture 分层原则、**手动依赖注入（DI）** 而非 Hilt 的取舍、**Ports & Adapters**（接口端口 + 替换实现）如何让 ViewModel 可测，以及基于 **Java ServiceLoader** 的游戏插件机制与 `-Pgames` 裁剪能力。

---

## 1. 概览：一套"接近生产级"的模块树

项目被拆成 23 个 Gradle 模块，纵向分四层，依赖严格**单向向下**：

```
:app（薄壳装配 + MainActivity + widget/worker）
  │
  ├─ :feature:weather , :feature:settings
  │       │
  │       ▼
  ├─ :core:data（fetcher/repository/cache，通向第三方的端口实现）
  │       │
  │       ▼
  ├─ :core:domain（业务生成器：物候 GDD、季节提示、生活指数，Android Library）
  ├─ :core:network（OkHttp 拦截器/HTTP 封装）
  ├─ :core:model（纯数据模型 + 序列化）
  ├─ :core:common（工具：PerformanceMonitor 等）
  ├─ :core:designsystem（主题/组件/场景映射）
  ├─ :core:res-illustrations , :core:test-fixtures（资源 / 测试夹具）
  │
  └─ :game:api（接口契约）← :game:common/:game:jump/:game:star/:game:maze/:game:farm/:game:home/:game:hockey/:game:pool/:game:plane
```

关键在于**依赖方向**：`:feature` 依赖 `:core:*`，`:core:*` 之间也分层明确；游戏模块只依赖 `:game:api` / `:game:common` / `:core:*`，**绝不反向依赖 `:feature` 或 `:app`**。这让每个模块都能独立编译、独立测试，也支撑了后面的插件裁剪。

> 本文不重复"每个阶段怎么拆、工作量多少"（那在 `MODULARIZATION.md`），而是聚焦**架构风格背后的方法论**——这套模块树究竟靠哪几条原则压住了复杂度。

## 2. Clean Architecture 在 Android 的落地方式

Clean Architecture 的经典分层（Entities → Use Cases → Interface Adapters → Frameworks）在这里被裁剪为四层：

| 层 | 模块 | 职责 | 是否知晓 Android |
|----|------|------|------------------|
| 数据模型层 | `:core:model` | `WeatherSnapshot`、`DailyWeather` 等纯数据类 + kotlinx 序列化 | 仅序列化注解 |
| 领域层（算法） | `:core:domain` | GDD 物候、季节提示、生活指数/预警/建议生成器 | 是（Android Library，generator 直接消费 `Resources` 与 `R.string`） |
| 领域层（用例） | `:feature:weather` 的 `domain/CitySearchUseCase` | 城市搜索：本地目录优先，再限时合并远程 / Geocoder | 是（`Context` + coroutines） |
| 端口层 | `:core:data` 的 `WeatherPorts` | 定义 `WeatherFetcher` / `WeatherCache` 等接口（port） | 接口本身净空 |
| 适配层 | `:core:data`/`:core:network` 实现、`:feature:*` UI | 具体 HTTP、缓存、Compose UI | 是 |

**两条取舍值得记录**：

1. **领域层用"纯 Kotlin 对象"而非严格 Use Case 类**：`GrowingDegreeDays`、`SeasonTipGenerator` 是**顶级的纯函数对象**（带显式状态入参），不是被 DI 注入的接口。这样物候算法可以零依赖地被 JUnit 测（`GrowingDegreeDaysTest`、`SeasonTipGeneratorTest`）。这是"轻量 Clean"——保留"业务逻辑与框架解耦"的核心收益，不为了形式引入一整套 Use Case 类。
2. **`Repository` 是门面而非领域**：`WeatherRepository` 只是聚合 `ForecastFetcher` / `CitySearchFetcher` / `HistoryFetcher` 三个 fetcher 的门面（`fetchWeather` 直接转调 `forecast.fetchWeather`）。复杂决策（是否回退缓存）**上移到 ViewModel**（见 `docs/网络层拦截器缓存与离线降级.md`），保持 data 层简单。

## 3. 手动依赖注入：为什么不用 Hilt

### 3.1 `AppContainer` 作为单一装配点

依赖全部集中在**一个手写的 `AppContainer` class**（`app/di/AppContainer.kt`），通过 `property lazy` 实现单例与按需创建：

```kotlin
val httpClient by lazy { OkHttpClient.Builder()...build() }        // 共享连接池
val weatherRepository by lazy { WeatherRepository(resources, httpClient, searchHttpClient, json) }
val weatherCacheStore by lazy { WeatherCacheStore(appContext) }
val citySearchUseCase by lazy { CitySearchUseCase(weatherRepository, locationHelper) }
```

访问方式：`WeatherApp` 持有一个 `container`，`context.appContainer()` 取回：

```kotlin
fun Context.appContainer(): AppContainer = (applicationContext as WeatherApp).container
```

### 3.2 权衡：手写 DI vs 编译期 DI（Hilt/Dagger）

| 维度 | 手写 `AppContainer` | Hilt/Dagger |
|------|---------------------|-------------|
| 编译/运行时开销 | 极低，无注解处理 | 处理注解、生成代码 |
| 可读性/可追踪性 | 装配一目了然，跳转即源码 | 依赖隐式注入 |
| 圈复杂度 | 项目规模中等，依赖树浅，够用 | 依赖树深/复杂时更省心 |
| 测试 | 手动构造依赖即可（配合 port 替换） | 有自带测试支持 |

**关键判断**：本项目依赖图**浅且集中**（核心就一个天气链路 + 若干 Store + 少量 UseCase），手写 `AppContainer` 完全够用，还省去了 Hilt 的注解处理编译成本和对"DI 魔法"的调试。**代码里几乎每个依赖都是显式构造、显式注入**，这对以可读性为导向的项目是合理取舍。唯一的"隐藏单例"是 `OpenMeteoHttp`（`object`，版本号在启动时注入），其余都走构造器。

## 4. Ports & Adapters：让 ViewModel 真正可测

### 4.1 端口定义在 data 层

`core/data/.../WeatherPorts.kt` 定义**端口接口**：

```kotlin
fun interface WeatherFetcher {
    suspend fun fetchWeather(city: City): WeatherSnapshot
}
interface WeatherCache { suspend fun get(city: City): ... ? }
```

- **`WeatherFetcher` 是 `fun interface`**——测试里用一行 lambda 即可提供桩实现；
- `WeatherRepository` 实现这些 port，`WeatherViewModel` **只依赖 port 接口**而不是具体 Repository，因此单测能注入假实现。

### 4.2 测试桩

`WeatherViewModelTestHarness` 提供了替换的 fetcher/cache 桩（带 `weatherCallCount` 计数），使 ViewModel 的各种流程（成功 / air 失败降级 / 网络错误回退缓存 / 静默去重）都能**脱离真实网络**被断言（`WeatherViewModelSelectCityTest`）——这是 Ports & Adapters 的直接产物。

### 4.3 避免反向依赖的接口下沉

`WeatherPresentationEffects` 用「接口 + NoOp 默认实现」让 `:core:data` 能触发"换桌面图标""弹通知"这类副作用，**却不必反向依赖 `:app` 的 widget / 图标实现**——实现由上层注入。这是处理"下层要召唤上层"这类环形倾向的标准手法。

## 5. 游戏插件机制：Java ServiceLoader + 动态依赖裁剪

游戏模块是这套架构里最亮眼的插件化设计，分两层：

### 5.1 契约层 `:game:api`

```kotlin
interface GameEntry {
    val password: String          // 口令，如「#小熊跳跳」
    @get:StringRes val titleRes: Int
    @Composable fun Content(sceneCode, isDay, cityName, onExit, onOpenGame, otherGames)
}
```

`:game:api` 是**纯接口契约模块**（无实现），游戏模块依赖它并实现 `GameEntry`。关键是**游戏侧不 import 任何 `:feature` 类型**——`sceneCode/isDay/cityName` 只是运行期传入的值，天气联动通过"值传递"而非"类型依赖"（对比 `MODULARIZATION.md`「天气—游戏联动契约」）。

### 5.2 `ServiceLoader` 注册与装配

每个游戏模块用 **Java ServiceLoader** 声明自己的入口提供者：

```kotlin
// game/jump/.../BearGameEntryProvider.kt
class BearGameEntryProvider : GameEntryProvider {
    override val entry: GameEntry = BearGameEntry
}
```

模块在 `META-INF/services/com.xiaoxiong.weather.game.GameEntryProvider` 声明 provider；`:app` 用 `loadGameEntryProviders()` 装配：

```kotlin
fun loadGameEntryProviders(): List<GameEntry> =
    buildList {
        val providers = ServiceLoader.load(GameEntryProvider::class.java)
        for (provider in providers) add(provider.entry)
    }
```

`WeatherGameOverlay` 据此建立「口令 → 游戏」路由，`BearHomeEntry` 通过 `otherGames`（装配方注入的其余已启用游戏）动态展示游乐间入口。

**一个真实踩坑与回归测试**：provider 实现类**必须是普通 `class`（public 无参构造器），不能用 Kotlin `object`**——因为 ServiceLoader 反射 `newInstance()` 实例化 provider，而 `object` 的构造器是 private 的，会抛 `ServiceConfigurationError: Unable to get public no-arg constructor` 导致**启动即崩**。每个游戏模块都配了 `BearerXxxEntryProviderTest` 用真实 `ServiceLoader.load(...)` 回归校验这一点——这是个"看似不起眼、错了就崩在启动"的约定，专门用测试钉死。

### 5.3 `-Pgames` 动态裁剪

`:app` 的构建脚本用 `-Pgames` 属性控制游戏依赖：

```kotlin
val gameProjects = mapOf("jump" to ":game:jump", /* … */ "plane" to ":game:plane")
val enabledGames = ...  // 解析 -Pgames=all/none/'jump,star,...'
gameProjects.forEach { (id, path) ->
    if (id in enabledGames) "fullImplementation"(project(path))
}
```

- **未选中的游戏模块根本不参与编译与打包**——classpath 上没有其字节码；`ServiceLoader` 自然发现不到对应入口，装配列表自动为空；
- 比"源码集裁剪"更彻底（不选的模块连字节码都不存在）；
- `:app` 带 `full` / `lite` 两个 flavor，**lite 版零游戏依赖**（`game:api` 接口层保留约 1-2KB，但无任何实现），契合"lite 零痕迹"语义。

**设计价值**：接口契约（`GameEntry`）+ 运行期发现（ServiceLoader）+ 构建期裁剪（`-Pgames`）三件事组合，让"新增一个游戏" = "写一个模块实现 `GameEntry` + 提供一个 provider + 声明 services"——**对装配方零侵入**，且可按包体诉求选择性裁剪。

## 6. 依赖规则约束总结

| 规则 | 含义 | 保证 |
|------|------|------|
| `:game:*` 不依赖 `:feature:*` / `:app` | 游戏侧只消费 `GameEntry` 值参数 | 插件可独立编译、可裁剪 |
| `:core:domain` 为 Android Library | GDD / 季节算法是顶层对象 + 显式 `Resources` 入参（generator 消费 `R.string`） | 纯算法部分仍可裸 JUnit 测 |
| `:core:data` 不反向依赖 UI | `WeatherPresentationEffects` 用接口+NoOp 反转 | 避免模块环 |
| `:app` 是薄壳 | 只做装配（`AppContainer`）与启动 | 其余逻辑模块内聚 |
| feature 只依赖 `:core:*` | UI 层不复用彼此实现 | 降低横向耦合 |

---

## 7. 结语

这套架构最值得借鉴的，不是"拆了 23 个模块"这个形式，而是**一套让"模块化"真正值回票价的方法论组合**：

- **Clean Architecture 裁剪到够用**：纯逻辑（物候/游戏引擎）下沉为零依赖对象，上限可测；
- **手动 DI 恰到好处**：依赖图浅就用显式构造，换来可读与低魔法；
- **Ports & Adapters 让测试变真**：`WeatherFetcher`/`WeatherCache` 端口 + 桩实现，ViewModel 流程全部可脱离网络断言；
- **ServiceLoader + `-Pgames` 把插件化做到运行期与构建期两端完备**：既能在运行期发现，又能在构建期裁剪。

`AppContainer` + `GameEntry`/`GameEntryProvider` + `WeatherPorts` 三者，分别回答了"谁组装依赖、谁定义扩展点、谁隔离可测面"——这是比具体模块数量更本质的架构骨架。
