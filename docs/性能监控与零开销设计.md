# 性能监控与「零开销」设计技术说明

> 对应模块：`:core:common`
> 核心文件：`PerformanceMonitor.kt`
> 摘要：本文说明小熊天气如何实现一套**仅在 Debug 生效、Release 完全零开销**的应用级性能监控：固定容量无损环形缓冲、`volatile` 开关、按需启动的后台守护线程、分位数统计，以及一处**真实的多线程竞态 bug** 及其修复。

---

## 1. 背景与设计目标

移动端 UI 卡顿 / 冷启动慢 / 网络慢这类问题，只有在真实设备与真实用户流量下才会暴露。小熊天气需要一个**能常驻采集、又不污染被测性能**的监控层。设计目标被收敛为三条相互矛盾的要求：

1. **必须常驻**：冷启动耗时、首帧耗时、逐帧耗时必须在主线程现场记录，否则采集不到；
2. **绝不能拖慢被测路径**：埋点本身引入的开销（GC、锁竞争、线程唤醒）会反向污染 `frame` / `startup` 指标，造成"测误报"；
3. **Release 必须彻底消失**：发布包里不能留有定时线程、每次 60s 被唤醒的睡眠，更不能有可观测的性能损耗。

这三条构成了本文所有设计决策的出发点。

---

## 2. 总体架构

```
  业务调用方（冷启动 / OkHttp 拦截器 / 帧循环 / 内存采样）
            │  recordStartup / recordNetwork / recordFrame / recordMemory / recordCustom
            ▼
     PerformanceMonitor（object 单例）
       │ 若 enabled == false：单次 volatile 读后立即 return（零开销门槛）
       ▼
   环形缓冲 LongBuffer ×N（固定容量、LongArray、无分配、无 GC）
       │
       ▼
   后台守护线程（60s 一次汇总）→ 生成报告（avg / p50 / p95 / max / n）
       │
       ▼
   Logcat 输出
```

关键边界：**采集（record\*）与汇总（dump）解耦**——采集路径只做 `LongArray` 的原子写，任何格式化、排序、日志都放到后台线程，保证采集端 O(1) 且零临时对象。

## 3. 「零 Release 开销」的三重保障

### 3.1 单点开关：`volatile enabled`

```kotlin
@Volatile
var enabled: Boolean = false
```

- `WeatherApp.onCreate()` 里 `PerformanceMonitor.enabled = BuildConfig.DEBUG`。
- 每个 `record*` 方法第一行都是 `if (!enabled) return`——**一次 volatile 读**，命中即返回。Release（`enabled == false`）下，埋点调用退化为一次对一个 `false` 字段的读取，几乎零成本，且**不会捕获任何数据**。

### 3.2 环形缓冲：`LongBuffer`

采集的存储不是 `List<Long>` 或 `ArrayDeque`，而是手写的固定容量[^1]环形缓冲：

[^1]: 每个指标的容量 `BUFFER_CAPACITY = 64`。

```kotlin:core/common/src/main/java/com/xiaoxiong/weather/util/PerformanceMonitor.kt
internal class LongBuffer(
    private val capacity: Int,
) {
    private val buf = LongArray(capacity)
    private var head = 0
    private var count = 0
    ...
}
```

它用 `LongArray` 而非装箱后的 `List<Long>`，从而：
- **不产生任何临时对象**，采集路径零 GC 压力；
- 满了以后**覆盖最旧样本**（`head = (head + 1) % capacity`），天然是固定内存上限——无论 APP 运行多久，内存占用恒为 `64 × 8B × 指标数`，不会无界增长。

### 3.3 按需启动的后台线程

最初版本在 `object` 初始化时无条件启动日志线程，导致 **Release 包即使 `enabled=false`，线程仍每 60s 被 `Thread.sleep` 唤醒一次**——有真实的上下文切换开销，违反"Release 零开销"原则。

修复方式：线程改为 `by lazy` 且显式触发：

```kotlin
private val logThread: Thread? by lazy { createLogThread() }

fun startLoggingIfEnabled() {
    if (!enabled) return
    logThread
}
```

- `by lazy`：只有**真正访问**才创建线程；
- `startLoggingIfEnabled()` 里先判 `enabled`，`false` 直接返回，**连 lazy 都不会触发**；
- 因此 Release 包中日志线程**根本不存在**——零线程、零唤醒、零上下文切换。

## 4. 环形缓冲的并发正确性：一处真实 bug 与修复

`LongBuffer` 会被**多个 OkHttp dispatcher 线程并发写入**。主天气加载会同时发起 `forecast` + `air-quality` 两个异步请求，加上 `search`、雷达帧等，不同路径会并发调用 `recordNetwork`，最终并发落到 `networkBuffers` 里对应路径的同一个 `LongBuffer` 上。

### 4.1 竞态

`add()` 存在**非原子的读-改-写**：

```kotlin
buf[head] = value
head = (head + 1) % capacity
if (count < capacity) count++
```

`head`/`count` 不是原子的。两个线程交错执行 `read head → write buf → update head` 时，会：
- **写覆盖**：线程 A 写完 `buf[head]` 还没来得及推进 `head`，线程 B 又写在同一个 `head` 上；
- **计数虚高**：`count++` 与 `head` 推进不同步，`count` 可能超过实际写入数，造成后续 `snapshot()` 读到未初始化或过期数据。

这类竞态在 Debug 采集路径上不会立刻崩，但会让 p50/p95/计数**失真**——而监控的**唯一价值就是数据准确**。

### 4.2 修复

对 `add` / `clear` / `snapshot` / `size` 全部加 `synchronized(this)` 互斥：

```kotlin:core/common/src/main/java/com/xiaoxiong/weather/util/PerformanceMonitor.kt
fun add(value: Long) {
    synchronized(this) {
        buf[head] = value
        head = (head + 1) % capacity
        if (count < capacity) count++
    }
}
```

设计取舍：
- **锁粒度为单缓冲**，不同路径的缓冲互不阻塞，只有同路径的并发写入才串行；
- 该路径**仅 Debug 采集启用**，锁开销可忽略；
- 代码注释明确指出替代方案：若要彻底无锁，需把 `head/count` 改为 `Atomic` 并保证**单一写者**——因为当前是"多写者 + 单读者"，同步是本次修复更稳妥的答案。

对应的并发测试会同时开启多条线程、交替写入并校验硬不变式（`size ≤ capacity`、快照单调有序、样本无丢失叠加），确保修复后不再复现。

## 5. 分位数统计与报告

汇总在后台线程由 `report()` 生成。`LongBuffer.snapshot()` 返回排序后的快照，`statsString` 据此计算：

```kotlin
val avg = snapshot.average().toLong()
val p50 = percentile(snapshot, 0.50)
val p95 = percentile(snapshot, 0.95)
val max = snapshot.max()
// → "avg=…ms  p50=…ms  p95=…ms  max=…ms  n=…"
```

- **排序在快照副本上做**（`buf.copyOf(count).also { it.sort() }`），不污染原始环形缓冲；
- `percentile` 用线性插值索引 `(p * (size-1)).toInt().coerceIn(0, size-1)`，`p95` 比均值更抗极端噪声，能反映"长尾"的慢请求/慢帧；
- `n` 是有效样本数，帮助判断统计可信度（样本太少时 p95 抖动大）。

## 6. 各类指标与阈值

| 指标 | 采集入口 | 关注阈值 | 说明 |
|------|----------|----------|------|
| 冷启动 | `recordStartup` | `> 2000ms` 报警 | 应用冷启动到可交互耗时 |
| 逐帧 | `recordFrame` | 慢帧 `> 16ms` | 帧耗时（ns→ms），反映 UI 卡顿 |
| 网络 | `recordNetwork` | 慢请求 `> 1000ms` | 按路径分桶（`forecast`/`air-quality`/`search`…），网络恢复/重试都会计入 |
| 内存 | `recordMemory` | — | `totalMemory - freeMemory`，MB |
| 自定义 | `recordCustom` | — | 业务侧任意耗时埋点 |

慢请求 / 慢帧同时由 `AtomicLong` 计数器 `slowNetworkCount` / `slowFrameCount` 累计（跨 60s 周期归零），用于给出"慢事件总数"这一直观信号。

**报告示例**（Debug 下约每 60s 输出一次）：

## 7. 正确性与设计权衡小结

| 设计点 | 取舍 |
|--------|------|
| Debug-only 开关 | 牺牲"Release 也能观测"换"Release 绝对无负担" |
| 固定容量环形缓冲 + 覆盖写 | 牺牲"全部历史"换"恒定内存 + O(1) 写入" |
| 多写者同步 | 牺牲"无锁"换"数据准确"；Debug 下锁开销可接受 |
| 采集/汇总分离 | 把格式化、排序、日志代价隔离到后台线程，保证采集路径零 GC |
| `by lazy` 线程 | 把后台线程的创建推迟到真正需要时，杜绝 Release 空转唤醒 |

**这套设计的核心价值**：监控本身必须"足够便宜"，才配得上一直开着。否则监控打点越密，测出来的性能越失真——这是所有埋点框架最基本的悖论，本文的方案用「门槛开关 + 无分配存储 + 采集汇总分离」三招从结构上规避了它。
