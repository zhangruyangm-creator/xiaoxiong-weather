# 天气数据管线：物候、日照、季节与 WMO 映射技术说明

> 对应模块：`:core:domain`、`:core:data`、`:core:designsystem`、`:feature:weather`
> 核心文件：`GrowingDegreeDays.kt`、`SeasonTipGenerator.kt`、`WeatherScene.kt`、`WeatherCodes.kt`、`HistoryFetcher.kt`、`ForecastFetcher.kt`、`SunPath.kt`
> 摘要：本文说明小熊天气如何把一行 Open-Meteo 天气数据"翻译"成有意义的季节物候提示与场景演绎：生长积温（GDD）推算花期偏移、经验时令窗口结合海拔与纬度、WMO 天气码到场景/图标/文案的分层映射，以及日出日落驱动的太阳弧线。

---

## 1. 背景：从「数值」到「意义」

Open-Meteo 返回的是温湿度、天气码、日出日落这类**原子数值**。但一个天气 App 的价值在于把这些数值组织成**用户能直接感知的信息**。小熊天气做了三件"翻译"：

1. **现在是什么天**：WMO 天气码 → 场景 / 图标 / 文案（WeatherScene / WeatherCodes）；
2. **现在是第几季、花开了吗**：用**生长积温（GDD）+ 经验时令窗口**推花期偏移与季节提示（GrowingDegreeDays / SeasonTipGenerator）；
3. **现在几点、太阳在哪**：用 Open-Meteo 的日出日落时刻驱动太阳弧线与"生活片刻"（SunPath）。

这三层独立成文最合适，因为每层都有清晰的算法，且代表"天气 App 该如何做数据→语义转化"的通用思路。

---

## 2. 生长积温（GDD）与花期偏移

### 2.1 为什么用积温而不是"过了几天"

植物物候（何时发芽/开花/落叶）不是由日期驱动的，而是由**热量累积**驱动的：同样 20 天，暖春的积温远超冷春。做生意就要用"暖年提前、冷年推迟"的经验修正，这正是 **Growing Degree Days** 的用武之地。

### 2.2 计算

```kotlin
dailyGdd(meanT, baseT) = max(0, meanT - baseT)       // 基准温度 5.0°C
cumulativeGdd = 逐日累加 above                          // 得到累积曲线
```

- 采用**日均温** `temperature_2m_mean`（而非最高/最低），因为 Open-Meteo archive 直接提供均值；
- **基准温 5.0°C**：`DEFAULT_BASE_TEMP_C`，多温带植物的通用有效积温下界；
- 单日为负则取 0（低于基准温的日子不贡献积温）。

### 2.3 物候偏移天数 `shiftDays`

把「今年今日累积 GDD」与「常年今日累积 GDD」比较，换算成"提前/推迟多少天"：

```kotlin
diff        = normal.last() - thisYear.last()      // 常年 − 今年（今日累计）
recentRate  = (thisYear.last() - thisYear[n-8]) / 7.0   // 近一周积温增速（度/天）
shiftDays   = diff / recentRate
```

- `diff > 0` 表示常年比今年暖 → **今年推迟**（正数）；`diff < 0` 表示今年偏暖 → **提前**（负数）；
- 用"近一周积温增速"作为把"积温差"换算成"天数"的标尺，比固定系数更贴合当前气候；
- **数据不足则放弃**：今年或常年累积天数 `< MIN_DAYS(30)` 时返回 `null`（提示退回纯经验推算）；
- 常年曲线 `averageByDayOfYear` 把多年逐日温按"月日"对齐平均，**2/29 并入 2/28**。

### 2.4 数据获取与缓存

物候所需的历史常年数据来自 **Open-Meteo Archive（ERA5 再分析）**，`HistoryFetcher.fetchPhenologyShiftDays`：

- `start_date = (今年 − 5)-01-01`，`end_date = 昨天`（**ERA5 数据延迟约 1 天**）；
- `PHENOLOGY_YEARS = 6`（今年 + 前 5 年做常年平均）；
- 该请求**独立于主天气加载**，按"城市+年份"缓存（一天最多一次）；失败**静默退回纯经验推算**，不影响主界面。

## 3. 季节提示：经验时令窗口 + 海拔 + 纬度

`SeasonTipGenerator` 把上面算出的积温偏移，叠加到一个**经验时令窗口**上，生成"春花开 / 红叶 / 赏雪"之类的提示。

### 3.1 总偏移 = 海拔偏移 + 积温偏移

```kotlin
totalShift = reliefShiftDays(...) + phenologyShiftFor(...)
```

- **海拔偏移** `reliefShiftDays`：按地形带取**固定阶梯常量**（天数），海拔越高花期越晚：
  - 山地（`≥800m`）春花 +7、夏花 +5、秋花 −3、红叶 −5；
  - 高原（`≥1500m`）春花 +16、夏花 +10、红叶 −12；
  - 高原原（`≥3000m`）春花 +25、红叶 −14。
  - 代码注释提到"约每 100m 晚 3~4 天"，但实现是**按带取阶梯值**，并非每米线性——文档如实记录这一点，避免误写成连续公式。
- **积温偏移** `phenologyShiftFor`：暖年**春/夏/冬花提前**（直接加天数），但**秋花/红叶取反**——因为暖秋往往让红叶/桂花**推迟**而非提前。这是对"物候方向与季节类型相关"的精细处理。

### 3.2 纬度断点的经验窗口

各事件（春花/红叶/降水等）的时令窗口**按纬度分段**，如春花分 6 档（`|纬度| < 22 / <28 / <34 / <40 / <46 / 其余`）；**低纬 `|lat| < 22` 的红叶直接返回 `null`**（热带常绿、无红叶）。地面还会区分南半球——纬度 `< 0` 时把日期 **+6 个月对齐北半球窗口**，展示时再 −6 个月映回。

### 3.3 相位判定

```kotlin
ratio = elapsed / total            // 已过天数 / 窗口总长
ratio < 0.2 → STARTING（刚开始）
ratio > 0.8 → ENDING（快结束）
else        → PEAK（正值高峰）
```

`daysUntil in 0..14` 判定"即将进入"，用于提前提醒。

> 重要边界：代码注释明确这是**经验时令**（基于统计的经验窗口），**不是观测物候**。GDD 只提供"偏暖/偏冷"的偏移修正，让经验窗口更贴近现实，但不确定真实花期。

## 4. WMO 天气码 → 场景 / 图标 / 文案 的分层映射

WMO 天气码（0~99）被**三层各自消费**，每层都是独立映射表：

### 4.1 场景层（WeatherScene）

天气码先归一为**场景枚举**，用于 UI 主题与背景美术：

| 场景 | 天气码 |
|------|--------|
| CLEAR | 0, 1 |
| PARTLY_CLOUDY | 2 |
| OVERCAST | 3 |
| FOG | 45, 48 |
| DRIZZLE | 51, 53, 80 |
| RAIN | 55, 61, 63, 81 |
| HEAVY_RAIN | 65, 82 |
| FREEZING_RAIN | 56, 57, 66, 67 |
| THUNDER | 95, 96 |
| HAIL | 99 |
| SNOW | 71, 73, 77, 85 |
| HEAVY_SNOW | 75, 86 |
| UNKNOWN | 其余（兜底） |

> 注：场景层与文案层对个别码的口径略有差异（如实记录而非对齐）——例如 `80`（阵雨）在场景层归 `DRIZZLE`，在文案层 `descriptionRes` 归 `rain_showers`。这是"美术场景"与"语义文案"两层独立映射的自然结果，二者互不覆盖。

### 4.2 归一化与文案层（WeatherCodes）

- **`normalizeCode`**：`code == 96 → 95`——雷暴伴轻微冰雹误报率高，统一按雷暴处理（`99` 保留冰雹）。**所有入口（预报/历史）解码后都统一调用**，保证全链路口径一致。
- **`descriptionRes`**：码 → 中文文案，未列出的码走 `wx_code_fallback` 兜底（内嵌码号展示），避免"未知天气码 → 空文案"。
- **强度分档**：`rainIntensity` 按**小时雨量**分档（`<0.1` NONE / `≤1` LIGHT / `≤4` MODERATE / `<16` HEAVY / `≤32` TORRENTIAL / `>32` VIOLENT）；`snowIntensity` 按雪码分档（`86` BLIZZARD、`75` HEAVY、`73` MODERATE、其余 LIGHT）。
- **`displayCode`**：当**实测雨/雪量与天气码不一致**时提升展示码（例如预报说毛毛雨但实测大雨），`keepCodeAsIs = {56,57,66,67,95,96,99}` 保留部分码不提升。

### 4.3 图标层（WeatherIcon）

按场景**自绘**（非图片资源）：CLEAR 白天画太阳 / 夜晚画月亮，雨滴数、雪花数按上文强度分档取量，不同场景不同配色。这使图标与场景严格同步，且天然适配深浅主题。

> 设计要点：把"码 → 场景"（美术/主题）、"码 → 文案/强度"（语义）、"码 → 图标"（图形）三层解耦，各自维护映射，避免一处改动牵连全局；`normalizeCode` 作为第一道统一闸口，收敛了 WMO 的细微差异（96/95）。

## 5. 日照：日出日落与太阳弧线

### 5.1 时刻来源

日出日落时刻**直接来自 Open-Meteo 返回的 `daily.sunrise` / `daily.sunset`**（预报与历史都请求），由 Open-Meteo 内部的标准太阳位置算法给出。**本应用不自行做天文计算**（Zeller / NOAA 式推算），只消费结果。

### 5.2 太阳弧线的"进度"是严格的线性映射

`SunPath.sunPathPhase(sunrise, sunset, now)`：

```
白天：elapsed / dayTotal   （0 = 日出，1 = 日落）
夜晚：elapsed / nightTotal （0 = 日落，次日 sunrise = 1）
若 !sunset.isAfter(sunrise)：返回 null（不画弧）
```

- 它是一个**按钟点的时间线性插值**，不是太阳高度角/方位角的天文算法——文档必须如实区分：**进度 = 时间比例**，而非日照几何；
- **极昼/极夜的唯一处理**：`sunset` 不晚于 `sunrise`（如高纬极昼没有"日落"）时直接返回 `null`，即不画弧、不给相位——没有额外天文修正。

### 5.3 让画面更"活"的辅助

- `dailyVariantIndex`：用质数乘子 `epochDay * 1_000_003 + salt.hashCode()` 生成**当天稳定的整数**，选当日插画变体（同日不变、跨日变化）；
- `sunPathBearMoment`：按**钟点**决定小熊的"生活片刻"——白天分工作日/周末，`isAlmostDawn` 用 **sunrise 前 30 分钟**精确判断（无 sunrise 时退回用 `nightProgress > 0.96f` 兜底），驱动"清晨准备上班"等插画。

---

## 6. 小结

| 层次 | 输入 | 算法 | 输出 |
|------|------|------|------|
| GDD 物候 | 历史日均温曲线 | 逐日积温 + 常/今年对比 ÷ 近期增速 | 花期提前/推迟天数 |
| 季节提示 | 偏移天数 + 纬度 + 海拔 | 阶梯海拔偏移 ± 积温方向修正 + 纬度断点窗 | 春/夏/秋/冬事件与相位 |
| WMO 映射 | 天气码 + 实测雨雪量 | 归一化 + 三层映射表 + 强度分档 | 场景/文案/图标 |
| 日照 | 日出/日落时刻 | 时间比例线性插值（无天文算法） | 太阳弧线进度 / 生活片刻 |

**核心价值**：这四层共同回答了天气 App 的"最后一公里"——把原子数值变成人的感知。积温让季节提示"感知冷暖"，三层 WMO 映射让"一个码"在不同界面各得其所，日照线性映射让太阳弧线"诚实反映时刻"。其中尤以 GDD 的"用近期增速把积温差换算成天数"、以及"秋景偏移取反"两处，是超越简单查表、真正体现领域理解的设计。
