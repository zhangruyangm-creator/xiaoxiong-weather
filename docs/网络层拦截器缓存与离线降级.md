# 网络层：OkHttp 拦截器、多级缓存与离线降级技术说明

> 对应模块：`:core:network`、`:core:data`、`:app:di`
> 核心文件：`RetryInterceptor.kt`、`PerformanceInterceptor.kt`、`OpenMeteoHttp.kt`、`WeatherCacheStore.kt`、`PhenologyCacheStore.kt`、`HistoryFetcher.kt`、`NetworkMonitor.kt`、`WeatherViewModel.kt`、`AppContainer.kt`
> 摘要：本文说明小熊天气如何基于一个共享的 OkHttpClient，用拦截器链实现"性能埋点 + 幂等重试"，用 DataStore 实现应用级缓存，用 ViewModel 实现"先展示缓存、失败回退缓存"的离线降级，并在网络切换时清空死连接。

---

## 1. 总体分层

网络层自底向上分四道：

```
View / WorkManager / Widget
   │
   ▼
ViewModel（读缓存先行 → fetch → 成功写缓存 / 失败回退缓存）   ← 离线降级发生处
   │
   ▼
WeatherRepository（门面，聚合 3 个 fetcher）
   │
   ▼
Fetcher（ForecastFetcher / CitySearchFetcher / HistoryFetcher / RadarMapRepository）
   │
   ▼
OpenMeteoHttp（通用 GET 封装：UA/Accept、错误→领域异常）
   │
   ▼
共享 OkHttpClient（拦截器链 + 磁盘缓存 + 超时 + 连接池）
```

值得写成文档的是三块：**拦截器链的顺序与职责**、**两套缓存（磁盘 HTTP 缓存 / DataStore 应用缓存）的边界**、以及 **ViewModel 的"成功先读、失败回退"降级策略与网络恢复**。

## 2. 共享客户端与拦截器链

### 2.1 单一共享 OkHttpClient

`AppContainer` 构造**一个共享的 `httpClient`**，天气主加载、搜索、雷达都由它派生（`newBuilder()`），从而共享同一磁盘缓存与连接池：

```kotlin
OkHttpClient
    .Builder()
    .cache(httpCache)                        // 20MB http_cache 磁盘缓存
    .addInterceptor(PerformanceInterceptor())  // 外层：计时（含重试在内）
    .addInterceptor(RetryInterceptor())        // 内层：幂等 GET 重试
    .connectTimeout(20, SECONDS)
    .readTimeout(10, SECONDS)
    .callTimeout(15, SECONDS)                 // 总耗时上限
    .retryOnConnectionFailure(true)
    .build()
```

**拦截器顺序很关键**：`addInterceptor` 按添加顺序进入 application interceptor 链，**先加的在外层**。因此链为：

```
PerformanceInterceptor → RetryInterceptor → OkHttp 内核（Cache/连接池/超时）→ 对端
```

含义：**Performance 记录的是包含 Retry 循环在内的整条链耗时**——从 `PerformanceInterceptor` 的 `SystemClock.elapsedRealtime()` 到返回，中间的每次重试（`Thread.sleep` + 再次 `chain.proceed`）都算入该请求耗时。

### 2.2 超时三重奏与"黑洞连接"

- `connectTimeout 20s`：建连等待；
- `readTimeout 10s`：首字节响应等待；
- **`callTimeout 15s`：整条调用（含重试）的总上限**。

代码注释点出了它的实战意义：**VPN / 半死连接黑洞**会把 connect + read + 重试累计到 30~40s，期间 UI 一直 loading 且不显示离线缓存。`callTimeout` 强制整条调用 15s 内失败，让 ViewModel 尽快回退到本地缓存 + 离线标识——**用总耗时上限换取降级时效**。

`searchHttpClient` 用更激进的 `connect/read 5s, call 6s`（搜索要响应快），`radarHttpClient` 用 `connect 8s / read 12s`（雷图瓦片大）。

### 2.3 RetryInterceptor：幂等 GET + 指数退避

```kotlin
maxRetries = 2，baseDelayMs = 400
重试条件 = 幂等(GET) && attempt < maxRetries && (code == 429 || code in 500..599)
退避 = baseDelayMs * (1L shl (attempt - 1))   // 400ms → 800ms
```

- **只重试 GET**：`request.method.equals("GET")`，因为只有 GET 幂等，POST 类请求失败直接抛，避免重复提交副作用；
- 网络抛 `IOException`（连接失败/超时）也进入重试，非 GET 或达上限才抛出；
- 重试间用**阻塞 `Thread.sleep`**，被中断时 `Thread.currentThread().interrupt()` 并抛出 `lastError ?: IOException("retry interrupted")`；
- 收到可重试响应后先 `response.close()` 再进入下一轮，释放连接。

### 2.4 PerformanceInterceptor：与监控层打通

`PerformanceInterceptor` 用 `SystemClock.elapsedRealtime()` 包住 `chain.proceed`，成功按 `response.isSuccessful`、失败按异常，写入 `PerformanceMonitor.recordNetwork(pathLabel, duration, success)`。标签取 encodedPath 中**最后一个"不以 v 开头且非 api"的路径段**：`/v1/forecast` → `forecast`、`/v1/air-quality` → `air-quality`、`/v1/search` → `search`。

这套埋点只在 `PerformanceMonitor.enabled = BuildConfig.DEBUG` 时开销，Release 零开销（见 `docs/性能监控与零开销设计.md`）。

### 2.5 OpenMeteoHttp：错误→领域异常

`OpenMeteoHttp` 是通用 GET 封装：注入 `Accept: application/json` 与 `User-Agent`（`XiaoxiongWeather/<版本> (Android)`，版本号启动时由 `AppContainer` 注入）；非 `2xx` → `AppError.Http(code)`，`IOException` → `AppError.NetworkUnavailable`。超时不在此设置（由传入 client 决定）。这样上层只依赖领域异常类型，不感知 HTTP 细节。

## 3. 两级缓存：谁负责什么

| 缓存 | 载体 | 容量 | 键 | 保鲜 | 用途 |
|------|------|------|-----|------|------|
| **HTTP 磁盘缓存** | OkHttp `Cache`（20MB） | — | URL | 由 HTTP 响应头决定 | 原始网络响应复用（省流量/加速） |
| **WeatherCacheStore** | DataStore Preferences | 12 条 | 城市（经纬度差 < 0.01） | **无保鲜（ViewModel 决定）** | 天气快照，供离线回退 |
| **PhenologyCacheStore** | DataStore Preferences | 24 条 | 城市 + 年份 | **`isFreshToday`：跨天即失效** | 积温偏移结果，一天最多查一次 |

### 3.1 HTTP 磁盘缓存 vs DataStore 应用缓存

- **HTTP 磁盘缓存**在 OkHttp 内核层，自动按响应头（`Cache-Control` 等）换新，**纯加速**，不承载"离线展示"语义；
- **DataStore 应用缓存**被 ViewModel 主动读写，**承载离线降级**——离线时从它取快照展示。它容量的差异也反映用途：天气 12 条足够覆盖最近查过的城市，物候 24 条覆盖多年窗口。

### 3.2 WeatherCacheStore 的"无保鲜"是有意的

`CacheEntry` 只记 `savedAtEpochMs`，**本身不做过期判断**。保鲜/降级策略**全部在 ViewModel 层**决定（见 §4）——缓存层保持"哑存储"，策略上移，职责更清晰。

### 3.3 PhenologyCacheStore 的"跨天失效"

`isFreshToday()` 用 `ChronoUnit.DAYS.between(fetchedDate, 今天) < 1` 判定——**物候快照一天内有效，跨天重取**。并且**存 `null` 表示"尝试过但无数据"**，当日不再重试（避免对同一城市反复打 ERA5）。

## 4. 离线降级："先展示、失败回退、恢复自刷"

真正的降级策略在 `WeatherViewModel`，有一套完整的状态机（这不是缓存层，而是用缓存做降级）：

### 4.1 成功式：先读缓存立即展示

非静默读取时先 `readCacheSafely(city)` 立即展示缓存（带"缓存时间"时间戳），再发起网络刷新——**用户先看到旧数据，再被新数据替换**，绝大多数情况感觉不到加载。

### 4.2 失败式：回退到缓存 + 离线标识

`fetchWeather` 失败 → catch → `readCacheSafely` → 有缓存则 `publishWeather(isOffline = true, errorMessage = "网络错误，已显示缓存")`；**无缓存才真正报错**。`readCacheSafely` **吞掉 DataStore IO 异常**，避免"缓存读失败导致永远 loading"。

### 4.3 去重与恢复

- **静默刷新去重窗口** `refreshDedupWindowMs = 5000`：5s 内不重复静默刷，避免并发触发连打网络；
- **网络恢复自动刷新**：`NetworkMonitor` 把在线状态暴露为 `isOnline`，`startNetworkRecoveryRefresh` 监听"离线→在线"转变，转正时自动 `refresh(quiet = true)`——**从离线回到在线能立刻补齐数据**，无需用户手动下拉。

## 5. NetworkMonitor：清空死连接 + 在线状态

```kotlin
registerDefaultNetworkCallback(...)
onLost        → connectionPool.evictAll(); _isOnline = false
onAvailable   → evictAll(); 再按 capabilities 更新在线
变为在线      → 再 evictAll()
在线判定       = NET_CAPABILITY_INTERNET && NET_CAPABILITY_VALIDATED
```

- **网络切换瞬间清空连接池**：Wi-Fi↔蜂窝切换后，旧传输上的 TCP 连接可能"半死"，继续复用会触发漫长的失败；`evictAll()` 强制后续请求重建连接；
- **在线判定用 `VALIDATED`**：不仅"有网"，还要"已被系统判定可访问互联网"，避免连上了一个没外网的 Wi-Fi 却当作在线；
- **连接池用 OkHttp 默认**（空闲 5、keepAlive 5min），未自定义；天气/搜索/雷达因 `newBuilder` 派生共享同一连接池。

## 6. 并发模型小结

| 场景 | 并发方式 |
|------|----------|
| 主天气加载 | `ForecastFetcher` 用 `coroutineScope { async }` **并行**拉 forecast + air-quality；air 失败静默降级为 `null`（不阻塞主加载，但透传 `CancellationException`） |
| 城市搜索 | **三路并发**：主查询 + 拼音补充 + 英文别名；主查询错误抛出，补充路静默 |
| 雷达 | `Semaphore(PREFETCH_PARALLELISM = 6)` 限并发预取；拼图时 `async` 并发取瓦片 |

这些并发与 `PerformanceMonitor` 的 `LongBuffer` 多写者并发，正是 `docs/性能监控与零开销设计.md` 里"同步环形缓冲"要解决的输入来源。

## 7. 设计权衡小结

| 设计点 | 取舍 |
|--------|------|
| 共享 client + `newBuilder` 派生 | 复用连接池/磁盘缓存；代价是共享配置（如 callTimeout）需在派生层显式覆盖 |
| 拦截器顺序（Perf 在外、Retry 在内） | Perf 度量含重试的整条耗时；代价是"纯网络耗时"需另行区分 |
| `callTimeout 15s` | 用总耗时上限换"快速失败回退缓存"；代价是极弱网下可能提前放弃 |
| 只重试 GET + 指数退避 | 安全重试；代价是 POST 失败不自动恢复（业务需自行处理） |
| 缓存"哑存储"、策略上移 ViewModel | 缓存层可复用、降级策略集中；代价是与 ViewModel 深度耦合 |
| 网络切换 `evictAll` | 避免复用半死连接；代价是切换瞬间需重建连接 |
| `VALIDATED` 判在线 | 避免"假在线"；代价是判定依赖系统校验时机 |

**核心价值**：网络层没有引入重型框架，用**共享 client + 两个拦截器 + 两级缓存 + ViewModel 状态机**就搭出了"有性能埋点、有安全重试、有离线兜底、能自动恢复"的完整能力。其中最值得借鉴的，是 `callTimeout` 作为"总闸"让整套超时/重试在未来得及拖垮 UI 前收敛，以及把"缓存存储"与"缓存策略"解耦，让降级逻辑集中且可测。
