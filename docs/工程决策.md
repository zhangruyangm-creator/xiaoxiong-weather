# 工程决策与教训记录

本文件记录**做错的事**及其根因。写在这里是因为：同一个根因已经连续造成三次返工，
而前两次我都没有把它当成"流程缺陷"而是当成"单个 bug"来修。

---

## 1. 逻辑层测试全绿 ≠ 玩法能玩

### 发生了什么

「小熊雨幕」在 1.16.0 发布后完全不可玩，随后修了三次（1.16.1 / 1.16.2 / 1.17.0），
每次都是真实缺陷，但始终没能让它好玩：

| 版本 | 缺陷 | 我的"验证" |
|------|------|-----------|
| 1.16.0 | 引擎返回**屏高比例**坐标，渲染层**当像素**用 → 方块画在 y≈0 处不动，2 秒后判漏接、0 分结束 | 50 个单测全绿 |
| 1.16.1 | 底部小熊条 `Canvas` 只有 `fillMaxWidth()` **无高度** → Spacer 量成 0 高度，小熊完全不显示 | 构建通过 |
| 1.16.2 | 背景雨丝用 `%`，负余数把雨丝画到屏幕外 | 纯逻辑测试全绿 |
| 1.17.0 | — | 仍不可玩（判定窗过窄、反馈缺失） |

### 根因

**我测的全是"我认为对"的东西，没有一项检验"好不好玩"。**

具体地说，三种验证手段全部失效：

1. **单元测试只覆盖引擎层。** 引擎内部的归一化数学是自洽的（`0.42 < 0.82`），
   所以 50 个测试全绿；而"把归一化值当像素"这个错误发生在**引擎与渲染的交界处**，
   那一行代码没有任何测试覆盖。
2. **数值分析不等于手感。** 我用 Python 算出点击速率 1.2→5.9 次/秒、峰值反应时间 0.71s、
   "同一时刻最多一块可点"，还为这些加了断言——数值全部合理，
   但**命中窗实际只有约 195ms**，玩家根本点不准，而这些断言一条都没能发现。
3. **手画预览图给了虚假信心。** 我用 Python 按配色与几何画了一张"看起来没问题"的图，
   但那个脚本**自己手算像素坐标、没有调用游戏真正的绘制函数**——
   所以它验证的是"我的设计意图"，不是"程序的真实输出"。
   真实的单位错误正是这样逃过了我的眼睛。

### 代价

- 连续发布 4 个版本（1.16.0 – 1.17.0），其中 3 个包含不可玩的游戏
- 把已知损坏的构建推到了公开下载页
- 消耗了用户反复真机测试来发现问题的时间

### 规则（以后必须遵守）

1. **涉及"手感 / 画面 / 时序"的改动，未经真机试玩不得发版。**
   构建通过、单测全绿、数值合理，**都不构成可玩性证据**。
2. **表现层不是测试盲区。** 若某个模块的代码从未被任何测试触达，
   就不能说它"验证过"。宁可写一个粗糙的截图对比，也好过零覆盖。
3. **预览/模拟工具必须复用被测的真实代码路径。**
   自己另写一份实现等于验证了自己的意图，不是验证了程序。
4. **新增"手感类"玩法（音游、跑酷等）时，先做最小可玩原型并让用户上手试**，
   再谈引擎、区分度、文档。顺序反了就会像这次一样，在没人玩过的情况下堆完 1500 行。

## 2. 用"完整性"替代"单位体积的体验收益"

同一个错误的另一个表现，值得单独记：

- **音游缺口**：判断"音游是最大浪费"是对的，但没论证"音游做得值"。
  结果做出来的是**占空间最大 + 有原理性缺陷（未接音频时钟）+ 唯一玩不到底**的最差组合。
- **BGM 缺口**：判断"8 款游戏没 BGM 是浪费"是对的，但没逐款论证必要性。
  7 首循环 BGM 共 9.3MB、占 APK 26%（WAV 是 PCM，deflate 压不动），
  而"每款游戏都有音乐"并不改善任何一款的可玩性。

**规则：补齐"缺口"之前，先算清单位成本，并逐项论证收益。**
"整齐"不是收益，"每 MB 换来多少体验"才是。

## 3. 附带破坏：正则误伤邻近代码

删 BGM 接线时用的正则把 `BearMazeScreen.kt` 里一条**原有注释**
（记录 `GameFrameLoop` 停帧语义）一起吃掉了。纯逻辑测试不会发现注释丢失。

**规则：批量文本改写后，必须 diff 逐个受影响文件确认没有误伤**，
并对"注释行数"这类无功能影响的内容也做一次核对。
