# 小熊摘星：程序化平台生成、跳跃物理与相机系统技术说明

> 对应模块：`:game:star`（小熊摘星）
> 核心文件：`BearStarJumpScreen.kt`（`StarJumpGame`）、`StarJumpLogic.kt`（引擎层）
> 摘要：本文说明一个竖版跳台游戏如何用「程序化平台生成 + 单轴跳跃物理 + 只上不下的相机」拼接出无限向上升空体验，并解释其难度曲线、环绕世界、平台接触判定的设计，以及引擎层如何保证玩法逻辑可测。

---

## 1. 背景与核心玩法

小熊摘星是竖版跳台（类似 Doodle Jump）：拖动控制熊左右移动，踩云向上弹跳，目标是升得越来越高、吃掉沿途的星星。与跑酷（`docs/小熊跳跳2D物理引擎与帧渲染.md`）不同，这里的核心张力来自：

- **一个二维可玩世界实际上被压缩成"接近一维"的攀爬**——水平只有宽屏内的左右移动，真正持续的挑战在垂直方向；
- **世界是无穷的**：平台必须**程序化生成**、随相机上移循环补充，并在屏幕下方回收；
- **物理只关心一条轴**（垂直），但横向有**环绕（wrap-around）**这一特殊语义。

值得写成文档的是三件事：程序化平台生成的**难度曲线**如何设计、跳跃/接触判定如何既"宽容"又"规则清晰"、以及"只上不下"的相机如何与生成/回收形成闭环。

## 2. 坐标系约定

| 量 | 约定 |
|----|------|
| `bearX` | 熊中心 x，**屏幕坐标**，可环绕（见 §6） |
| `bearY` | 熊中心 y，**世界坐标，向上为负** |
| `cameraY` | 屏幕顶对应的世界 y |
| `s` | 屏幕缩放（对所有尺寸量生效） |

"向上为负"可能反直觉，但好处是：升得越高，`bearY` 越小，`cameraY` 越负；海拔用 `altitudeKm = (-cameraY / (2400·s)).coerceAtLeast(0)` 换算成"公里"，用来在 HUD 上展示"你登上了多高"。

## 3. 跳跃物理：单轴显式欧拉

垂直推进极简——`stepFalling` 做一帧显式欧拉：

```kotlin
nvy = bearVY + g * dt      // g = 2600·s
ny  = bearY  + nvy * dt
```

熊的"跳跃"其实没有主动向上的力，而是**从平台获得的反弹初速**在重力下抛物线：

| 来源 | 反弹初速 |
|------|----------|
| 普通 / 碎台 | `bounceV = -1350·s` |
| 弹簧台 | `springV = -2350·s` |

横向则是**手指跟随**的阻尼控制（`bearVX += (desired - bearVX) * min(1, dt*11)`，无触摸时指数衰减 `bearVX *= 1 - min(1, dt*2.2)`）。横向不是刚性锁定而是"追目标"，移动手感更柔，也避免拖拽时瞬间瞬移。

## 4. 平台接触判定：宽容但规则清晰

平台碰撞只在**下落且脚线穿越台面**时判定（`resolveContact`，见 `StarJumpLogic`）：

```
若 bearVY <= 0：不判（上升/静止不落台）
否则对每个未碎平台 p：
    p 在屏幕内（p.y - cameraY <= h + bs）才考虑
    若 上一帧脚线 prevFeetY <= p.y 且 本帧脚线 newFeetY >= p.y（脚线穿越台面）：
        计算水平偏差 dx（含环绕修正）
        若 |dx| < p.w/2 + bs·0.24 → 命中：
            落地 y = p.y - bs/2
            反弹速度 = 弹簧 ? springV : bounceV
```

几个刻意设计：

1. **只用"脚线"而非整熊 AABB**——垂直判定专注一条线，配合下落方向，天然避免"上升时头撞平台"这类 bug；
2. **水平宽容 `bs·0.24`**：熊的"腰椎"并不要求完全踩进台面，有约 1/4 熊宽的容错，体验更宽松；
3. **跳过已碎平台**（`p.broken` continue）——碎台一旦触发就去掉判定；
4. **死亡线**：`p.y - cameraY > h + bs` 的平台不可踩——已经滚出屏幕下方的不再作为落脚点。

命中后，普通/弹簧台更新位置并弹跳，**碎台（`BREAK`）置 `broken=true` 且计入 `breakT`**（随后破碎消失）。每类平台触发不同的表现副作用（普通 `onBounce`、弹簧震屏+`onSpring`、碎台 `onBounce`）。

## 5. 程序化平台生成与难度曲线

平台的"下一块"由一个**生成游标** `nextPlatY`（世界 y，向上递减）驱动，`genPlatforms` 用一个 while 把缺失区域补齐（`while (nextPlatY > limitY)`），在上方逐块往下铺：

### 5.1 进度归一

```kotlin
val progress = (-nextPlatY / (3400f * s)).coerceIn(0f, 1f)
```

`progress ∈ [0,1]` 表示"爬升阶段"。**所有难度参数几乎都以 `progress` 为自变量**，这就把"离地面的高度"直接变成了"难度标尺"。

### 5.2 类型分布的随高度演进（`platformShape`）

```kotlin
type =
    when {
        early -> NORMAL                 // 出生区（nextPlatY > -700·s）必为普通台
        roll < 0.07                    -> SPRING
        roll < 0.17 + 0.08 * progress  -> BREAK
        roll < 0.32 + 0.18 * progress  -> MOVING
        else -> NORMAL
    }
```

- **早期兜底普通台**：玩家熟悉操作前不出现弹簧/碎/动台；
- **BREAK/MOVING 的阈值随 `progress` 线性抬升**：越高，碎台与移动台占比越大，普通台的相对比例被挤压——难度单调递增；
- **SPRING 是固定奖励**（恒 7%）：弹簧带来高弹跳的爽快感，不受难度影响，是"偶尔的奖励峰"。

> 设计要点：**类型与横向落点解耦**。类型只由 `roll`（一个随机数）决定，而 `x`（横向位置）与移动台初速 `vx` 用**另外独立的随机数**决定——这样类型不与会"落在多难的位置"相关，避免"又难又刁"的叠加。

### 5.3 平台宽度随高度的收缩

```kotlin
pw = (150f - 26f * progress) * s          // 越高越窄
// 移动台再钳到可移动区间 55% 内：min(pw, maxTravel * 0.55).coerceAtLeast(48·s)
// 其它台：min(pw, maxTravel)
```

- 基础宽度从 `150·s` 线性收到 `124·s`；
- **越窄 + 越多移动/碎台 + 间距更大（见下）**，三者叠加让高处每一步都是"精确落点"；
- 移动台宽度被钳到其可移动行程（`maxTravel`）的 55% 内，避免移动台太宽导致"无处可躲"。

### 5.4 垂直间距与星星点缀

```kotlin
val gap = (95f + 78f * progress + Random.nextFloat() * 30f) * s   // 越高间隙越大
// 非早期且有 26% 概率在间隙中放一颗星星
```

间隙随高度增大（也就要求更大初速才能跨过——但弹簧给的 `-2350·s` 可以应对），星星以 `26%` 概率点缀在平台间隙处（`y = nextPlatY - gap*0.45`），把"冒险跳更高"与"收集奖励"耦合。

## 6. 环绕世界与只上不下的相机

### 6.1 横向环绕

熊越过左右边界会从对侧出现：

```kotlin
if (bearX < -bs * 0.5f) bearX += w + bs
if (bearX > w + bs * 0.5f) bearX -= w + bs
```

宽度上构成环形拓扑。这一语义在**接触判定里也必须一致**：`resolveContact` 与 `starPickup` 都对 `dx` 做环绕修正（`if (dx > w/2) dx -= w+bs; if (dx < -w/2) dx += w+bs`），否则"从左边出、右边进"时对极远平台的接触判定会出错——这类"坐标环绕与物理判定必须同步"的隐式约束，正是易惹 bug 处，也是值得记录的设计。

### 6.2 相机"只上不下"

```kotlin
val target = bearY - h * 0.42f
if (target < cameraY) cameraY = target   // 只在熊更靠上时上移
```

- 相机**只会上移、永不下移**——放任玩家下落回低处，但没有"被相机推着往下走"的容错，掉出底部就是死亡；
- 相机的**上移目标锁定熊上方 42% 屏高处**，保证玩家始终看到前方的云；
- **只上不下**让生成方向唯一化：只需"往上补"、只需"往下回收"。

### 6.3 生成与回收的闭环

每帧在相机上移后：

```kotlin
genPlatforms(cameraY - h * 0.5f)              // 向上补平台（含可能出现的星星）
platforms.removeAll { it.y > cameraY + h + 120f * s }  // 回收滚出屏下的平台
```

- 生成预算：只补到屏幕上方 `h*0.5` 的高度，避免一次性生成过多；
- 回收：`cameraY + h + 120·s` 以下的平台与星星直接移除——它们已不可达（且 `resolveContact` 里本就判它们"不可踩"），移除控制内存与遍历成本。

## 7. 死亡判定与难度收口

```kotlin
if (bearY - cameraY > h + bs) {
    phase = OVER
    onDeath(score)     // 掉出屏幕底部即死亡
}
```

死亡线是"屏幕底 + 一个熊高"，与接触判定的死亡线（`p.y - cameraY > h + bs`）**同一阈值**——这意味着"最后一块可踩平台恰好滚出屏幕时"也是熊坠落的死亡点。得分 `scoreFor(maxHeight, stars, s) = (-maxHeight/(60·s)).toInt().coerceAtLeast(0) + stars*25`——**核心指标是到达过的最大高度** `min(maxHeight, bearY)`，星星只是 +25 的加成。

## 8. 正确性与可测性：引擎层封装

与跑酷一致，这里的玩法核心**全部从 `StarJumpGame` 抽到 `internal object StarJumpLogic`**：`stepFalling`（垂直积分）、`resolveContact`（平台判定）、`starPickup`（星星吃取）、`platformShape`（类型/宽度）、`scoreFor`、`altitudeKm` 都是纯函数，显式接收 `w/h/s` 与当前状态而非读取可变字段。于是：

- **`resolveContact` 的每条分支**（上升不判、死亡线以下不可踩、碎台跳过、环绕水平偏差、弹簧/普通反弹、landY 计算）都能被 JUnit 精确断言；
- **`platformShape` 的分布**（早期兜底、随 progress 抬升的阈值、宽度钳制）能被统计性验证；
- 配合差分测试（parity test）可在**不改变随机序列**的前提下完成重构——因为 `x`/`vx` 的 `Random` 调用被保留在表现层，引擎层只消费已确定的 `roll` 值。

### 设计权衡小结

| 设计点 | 取舍 |
|--------|------|
| 单轴物理 + 环绕 | 玩法聚焦垂直、横向只需环绕，物理最简可测；代价是"环绕判定必须处处同步" |
| 类型-落点解耦（独立随机） | 避免"又难又刁"叠加；代价是引入两个随机数源 |
| 相机只上不下 | 生成/回收方向唯一化；代价是"往下掉"没有相机容错 |
| 宽度/间隙/类型随 `progress` | 单调难度曲线 + 可调；代价是需小心校准线性系数 |
| 引擎/表现分离 + 纯函数 | 玩法逻辑可单测；代价是多参数透传与 `internal` 可见性约束 |

**核心价值**：把一个"无限上升"体验简化为「一段可预算的程序化生成 + 一条轴的可测物理 + 一个单向相机」，并通过引擎层封装让最难的正确性判断（平台接触、分布演进、环绕修正）全部变成可复现、可断言的测试用例。
